# メモリ実測の記録

SPEC §9.1 の 4 条件と §9.1.1 の判断規則に基づく実測値。
フェーズ完了ごとに追記し、どのコミットで何が太ったかを追えるようにする。

計測は `make memcheck`（内部で `tools/memcheck.sh`）。
指標は Linux の `/proc/<pid>/smaps_rollup` の `Private_Dirty`（SPEC §9.1 の指標 A）。
**OpenBSD では `smaps_rollup` 相当が無いため指標 A を計測できない**（SPEC §9.1）。

> **⚠ Phase 1〜3 の絶対値は Phase 4 以降の値と直接比較できない。**
> Phase 4 で計測方法の欠陥（M1 と M20 を別プロセスで測っていた）を
> 修正したため。詳細は「Phase 4 完了時」の節を参照。

| 条件 | 内容 | 判定基準 |
| --- | --- | --- |
| M0 | 0 窓・タスクバー無効 | < 400 KB |
| M1 | 0 窓・タスクバー/トレイ有効 | < 550 KB |
| M20 | 20 窓 | `(M20−M1)/20 < 2 KB` **かつ** `M20 < 1024 KB` |
| M20h | M20 + 1 時間 + 500 回の開閉 | `M20h − M20 < 32 KB` |

---

## Phase 1 完了時（2026-08-08）

コミット: Phase 1 の全 15 モジュールがリンクし、Xvfb 上で動作。
装飾描画・タスクバー・トレイは**未実装**（Phase 2 以降）。

| 条件 | Private_Dirty | 判定基準 | 判定 |
| --- | --- | --- | --- |
| M0 | **232 KB** | < 400 KB | PASS |
| M1 | **228 KB** | < 550 KB | PASS |
| M20 | **252 KB** | 限界費用 1.2 KB/窓、< 1024 KB | PASS |
| M20h | 未計測 | — | — |

参考値（指標 B）: VmRSS ≈ 2,304 KB（0 窓）／ 2,320 KB（20 窓）。
共有ライブラリのテキスト領域を含むため主指標にはしない（SPEC §9.1）。

**窓あたりの限界費用 ≈ 1.2 KB**（別計測では 0.8 KB）。目標の 2 KB/窓を下回る。
`struct client` は約 448 B なので、残りはフレームウィンドウ関連の
xcb 内部バッファとプロパティ読み取りの一時領域と見られる。

### SPEC §9.1.1 の判定

M20 = 252 KB は **「< 400 KB → 目標は達成可能。そのまま全機能を実装する」** の帯。
削減順序（トレイ → スタートメニュー → タスクバー → …）の発動は不要。

### 注意（この数字の読み方）

これは**装飾描画・タスクバー・スタートメニュー・トレイが無い状態**の値である。
1 MB の予算に対して約 770 KB の余裕があるが、残りのフェーズで以下が乗る:

- Phase 2: テーマ配色表、グリフのラン分割キャッシュ、内蔵ビットマップフォント
  （`.rodata` は `Private_Dirty` に載らないが、フォント計測キャッシュは載る）
- Phase 4: タスクバー・スタートメニュー・トレイ（PLAN の想定増分は 150 KB 未満）

したがって現時点の PASS は「Phase 1 の設計判断が正しかった」ことを示すに留まり、
最終的な達成を保証しない。次の判定点は Phase 4 完了時（SPEC §9.1.1）。

## Phase 2 完了時（2026-08-08）

装飾描画・フォント・カーソル・ウィンドウメニューを実装した状態。
タスクバー・トレイは未実装（Phase 4）。

| 条件 | Private_Dirty | Phase 1 比 | 判定基準 | 判定 |
| --- | --- | --- | --- | --- |
| M0 | **236 KB** | +4 KB | < 400 KB | PASS |
| M20 | **260 KB** | +8 KB | 限界費用 1.2 KB/窓、< 1024 KB | PASS |

装飾一式（テーマ配色表・描画 GC・フォントのメトリクスとアトラス・
カーソル 11 種）を足しても**常駐の底は +4 KB** しか増えていない。
設計どおり、描画に必要なものはほぼサーバ側（GC・Pixmap・カーソル）に
あり、クライアント側に抱えているのは幅表とメトリクスだけであるため。

窓あたりの限界費用は 1.2 KB のまま変わらなかった。`struct client` には
タイトルの計測キャッシュ（`draw_glyphs` / `draw_ellipsis` /
`caption_w_at_measure`）と装飾の対話状態（`hover_part` / `press_part`）が
増えたが、合わせて 6 バイトなので測定粒度に埋もれている。

内蔵フォントは `.rodata` に 2,464 B（224 グリフ）。`.rodata` は
`Private_Dirty` に計上されないため、この指標には現れない。

### SPEC §9.1.1 の判定

M20 = 260 KB は引き続き **「< 400 KB → 目標は達成可能」** の帯。
残るのは Phase 4 のタスクバー・スタートメニュー・トレイで、
PLAN の想定増分は 150 KB 未満。仮にその 2 倍かかっても
1 MB には到達しない見込み。

---

### M1 < M0 について

M1（タスクバー有効）が M0（無効）より 4 KB 小さい逆転が出ているが、
これは計測ノイズである。Phase 1 時点ではタスクバーが未実装で、
設定キーを読む以外の差が無いため、両者は本質的に同じ構成になっている。
Phase 4 で実装が入れば正しい差が出るはずで、その時点で再確認する。

## Phase 3 完了時（2026-08-08）

EWMH の完全対応・`_NET_WM_SYNC_REQUEST`・`_NET_WM_PING`・アイコン読み込み・
CSD・Shape を実装し、実装バグを修正した状態。タスクバー・トレイは未実装（Phase 4）。

| 条件 | Private_Dirty | Phase 2 比 | 判定基準 | 判定 |
| --- | --- | --- | --- | --- |
| M0 | **248 KB** | +12 KB | < 400 KB | PASS |
| M20 | **276 KB** | +16 KB | 限界費用 1.4 KB/窓、< 1024 KB | PASS |

### バグ修正前は限界費用が超過していた

修正前の実測は M0=252 KB / M20=304 KB で、**窓あたり 2.6 KB** と目標の
2 KB を超えていた。原因は `deco.c` の `xcb_change_gc` の値の並び順の誤り
（下記）で、描画のたびに `BadPixmap` エラーが発生し、xcb のエラーイベントが
キューに積まれていた分である。順序を直したところ 1.4 KB/窓に戻った。

**限界費用のゲートが、絶対値に達するはるか手前で実バグを検出した。**
SPEC §9.1 を AND 条件にした狙いがそのまま働いた形になる。
「絶対値に余裕があるから問題ない」で流していたら、このバグは
Phase 4 以降まで残っていた。

### リーク検査

30 窓の開閉を 6 周した後の `Private_Dirty` は 276 KB で**平坦**
（1 周目 272 → 2 周目以降 276 で変化なし）。単調増加は無く、
スラブのチャンクと malloc アリーナが一度確保されて再利用される
設計どおりの挙動である。

### SPEC §9.1.1 の判定

M20 = 276 KB は引き続き **「< 400 KB → 目標は達成可能」** の帯。

タスクバー・システムトレイ・スタートメニュー・Alt+Tab スイッチャを実装した状態。
これで SPEC の常駐 UI は全て乗った。

| 条件 | Private_Dirty | 判定基準 | 判定 |
| --- | --- | --- | --- |
| M0 | **360 KB**（248〜368 の幅あり） | < 400 KB | PASS |
| M1 | **364 KB**（252〜368 の幅あり） | < 550 KB | PASS |
| M20 | **384〜396 KB** | 限界費用 **1.0〜1.4 KB/窓**、< 1024 KB | PASS |
| M20h | 計測中（下記） | `M20h − M20 < 32 KB` | — |

### 1. 計測方法が壊れていた（これが本節の主題）

Phase 3 までの `tools/memcheck.sh` は **M1 と M20 を別々に起動した WM で
測っていた**。限界費用のゲートはその 2 つの差を 20 で割る:

```
(M20 − M1) / 20 < 2 KB/窓
```

ところが同一バイナリでも起動直後の `Private_Dirty` は実測で
**248〜368 KB** ばらつく（malloc アリーナの初期状態と ASLR による）。
このばらつきは 20 で割ると **±3 KB/窓**。判定しようとしている
2 KB/窓より大きい。**つまりこのゲートは雑音を測っていた。**

実際、Phase 3 のコミットをこの環境で測り直すと:

| 計測方法 | Phase 3 の限界費用 |
| --- | --- |
| 旧（別プロセスの差） | 1.4 KB/窓 と記録されていた（M0=248, M20=276） |
| 旧（別プロセスの差、再実行） | 2.0 KB/窓（M1=356, M20=396） |
| **新（同一プロセスの差）** | **2.2 KB/窓（M1=348→M20=392）** |

同じコードが計測のたびに 1.4 / 2.0 / 2.2 と動いた。
**Phase 1〜3 の記録値は「そのとき偶然そう出た 1 標本」であり、
コードの性質ではなかった。**

修正は単純で、**1 つのプロセスで「0 窓 → 20 窓」の差を取る**。
そうすれば差に起動ごとのばらつきが乗らない。
併せて、20 枚が本当に**管理下に入った**ことを `_NET_CLIENT_LIST` で
確認するようにした（従来の `xdotool search` は xterm の内部ウィンドウも
数えるため、実際には 20 枚に届いていなくても先へ進んでいた）。

---

### 2. 直したうえで測ると、本当に超過していた

同一プロセスで測ると Phase 4 は **48〜52 KB / 20 窓 = 2.4〜2.6 KB/窓**。
Phase 3 も **2.2 KB/窓**。**どちらも 2 KB のゲートを超えていた。**
Phase 4 が足した分は差し引き 0.4 KB/窓しかなく、
**超過は Phase 1〜3 から存在していて、壊れた計測に隠れていた。**

どこに消えているかを `/proc/<pid>/smaps`（rollup ではなく領域別）で
0 窓と 20 窓で差分を取ったところ、増えたのは 2 箇所だけだった:

| 領域 | 0 窓 | 20 窓 | 差 |
| --- | --- | --- | --- |
| `[anon]`（BSS。スラブ chunk 0 と各種静的配列） | 28 KB | 48 KB | +20 KB |
| `[heap]`（glibc アリーナ） | 40 KB | 76 KB | **+36 KB** |

BSS 側の +20 KB は設計どおり（`struct client` 20 個分 ≒ 11 KB に、
`stack.c` の `WM_MAX_CLIENTS` 長の静的配列が先頭ページだけ触られる分が乗る）。

**問題はヒープの +36 KB で、これは「使っている」メモリではない。**
クライアントを管理に取り込むときプロパティ読み取りと xcb のリプライで
一時領域を確保しては解放するが、解放しても glibc のアリーナは縮まない。
窓あたり 1.8 KB 相当、つまり **2 KB/窓ゲートの大半がこの「返し忘れ」だった。**

### 3. 対策: アイドル時の `malloc_trim`

`main.c` のイベントループで、**イベントが 1 つも来なかった周回**かつ
**ドラッグ中でない**ときに 1 回だけ `malloc_trim(0)` を呼ぶ。
一度呼んだら次にイベントが来るまで呼ばないので、
「返した直後にまた確保する」振動は起きない。glibc 以外では no-op。

| | M20 − M1 | 限界費用 |
| --- | --- | --- |
| 対策前 | 48〜52 KB | 2.4〜2.6 KB/窓 **FAIL** |
| **対策後** | **20〜28 KB** | **1.0〜1.4 KB/窓 PASS** |

ドラッグ中を除外しているので §3.4.1 のペーシングには干渉しない。

### 4. 窓数を増やしたときの実際の傾き

同一プロセスで窓を増やしながら測ると、費用は線形ではない:

| 窓数 | Private_Dirty | 直前からの増分 |
| --- | --- | --- |
| 0 | 256 KB | — |
| 20 | 300 KB | +44 KB (2.2 KB/窓) |
| 40 | 308 KB | +8 KB (**0.4 KB/窓**) |

最初の 20 窓に一度きりの段差（静的配列の先頭ページ、xcb の内部バッファ、
アリーナの立ち上がり）が乗っており、**漸近的な限界費用は 0.4 KB/窓**。
`(M20−M1)/20` というゲートはこの一度きりの段差を窓数で割ってしまうため、
本来の窓あたり費用より厳しく出る。今回はゲートを緩めずに
一度きりの段差そのものを減らして通した。

### SPEC §9.1.1 の判定

M20 = 384〜396 KB は **「< 400 KB → 目標は達成可能。そのまま全機能を実装する」**
の帯（ただし Phase 3 までより余裕は小さい）。削減順序の発動は不要。

### 教訓

**限界費用のゲートは 2 回とも実バグを検出した。**
Phase 3 では `deco.c` の `BadPixmap`、Phase 4 では計測方法の欠陥と
アリーナの返し忘れ。いずれも絶対値（1 MB）にはまだ 600 KB 以上の
余裕がある段階で見つかっている。絶対値だけを見ていたら
どちらも Phase 5 以降まで残っていた。

## M20h の計測も壊れていた（2026-08-09）

`--long` を初めて回したところ、**1 時間待った末に "N/A" しか出なかった**。
しかも 1 時間で終わらず 2 時間以上回り続けていた。原因は 3 つ重なっていた。

### 1. ストレスが WM 自身を殺していた

`run_stress_cycles()` は対象ウィンドウを

```sh
xdotool search --onlyvisible --name '.*'
```

で選んでいた。これは**名前のある可視ウィンドウを無差別に返す**。
Phase 4 でタスクバーとトレイに `_NET_WM_NAME` を付けた結果、
これらが候補に混ざるようになり、3 周に 1 回の

```sh
xdotool windowkill "$win"
```

がパネルに当たった。`windowkill` は `XKillClient` なので、
**そのウィンドウを所有するクライアント = w98wm 自身の X 接続が切られる**。

WM のログには `X 接続が切れた` の 1 行だけが残っており、
計測開始から約 1 分で死んでいた。残りの 59 分は
**既に存在しないプロセスの `/proc/<pid>/smaps_rollup` を読もうとしながら**
回り続けていた。

対象は `_NET_CLIENT_LIST` から取るように直した。
ここには override-redirect のパネルは載らないので、原理的に自分を殺せない。
これは M20 の窓数の待ち合わせを直したときと**同じ間違い**である
（`xdotool search` は WM から見た「クライアント」とは別のものを数える）。

### 2. WM の死を検出していなかった

毎周 `kill -0 "$WM_PID"` で生死を見て、死んでいたら即座に打ち切るようにした。
1 時間待ってから「測れませんでした」と言うのは何の情報にもならない。

### 3. 1 時間で終わらなかった

`sleep 7.2` を 500 回、という固定間隔だったため、
`xdotool` の所要時間がそのまま上積みされていた。
特に `windowsize --sync` は、WM が `WM_NORMAL_HINTS` の
resize increment で要求値を丸めると一致せず、待たされ続ける
（xterm は文字セル単位なので必ず丸められる）。

- 間隔を**壁時計基準**にした（`started + seconds * idx / total` まで待つ）
- `--sync` を外した（ストレスをかけるのが目的で、正確なサイズは不要）
- 進捗を 5 分ごとに出すようにした。1 時間無言なのは追跡できない
- `M20H_SECONDS` / `M20H_CYCLES` で短縮できるようにした（動作確認用）

### 短縮版での確認

`M20H_SECONDS=150 M20H_CYCLES=50` で通しで確認したところ、
WM は最後まで生存し、`Private_Dirty` は **48 秒から 144 秒まで 276 KB で完全に平坦**、
`M20h − M20 = 0 KB` で PASS した。

### テストのプロセスリークも直した

この調査中に、**Xvfb が 24 個、w98wm が 17 個**、いずれも `PPID=1` で
孤児化した状態で残っているのが見つかった。`lib.sh` の `trap` は
`SIGTERM` を送るだけで、親シェルが先に終了すると取り残される。

- `lib.sh`: `SIGTERM` → 最大 2 秒待つ → `SIGKILL` の 2 段にした
- `tests/run-tests.sh`: 各テストの前後でサーバプロセスの一覧を取り、
  **増えた分をランナ側でも回収する**ようにした（二重の網）。
  対象は Xvfb と w98wm だけに絞る（xterm まで落とすと、
  同時に走っている `memcheck --long` の被験ウィンドウを巻き添えにする）

修正後、13 本 x 1 回の実行でリークは 0 になった。
