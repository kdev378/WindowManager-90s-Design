# 要求 → 実装 → 検証の対応表

SPEC の各要求が、どのコードで実装され、どのテストで検証されているかの一覧。
**「仕様に書いてある」と「テストがある」は別物**なので、
そこを混同しないための表である。

凡例:

| 記号 | 意味 |
| --- | --- |
| **自動** | `make test` で毎回検証される |
| **半自動** | テストはあるが、通る条件が緩い（存在確認どまり等） |
| **手動** | `docs/MANUAL-TEST.md` の項目。実環境が要る |
| **未** | 検証手段が無い。壊れても気づけない |

### 既知のフレーク

**無し**（2026-10-27 時点）。以前ここにあった 2 件はどちらもテスト側の不具合だった:

- `160-net-wm-state.sh` が負荷時にだけ落ちる … 検証クライアントが `xcb_flush` の
  直後に終了しており、負荷の高い X サーバが要求ごと接続を捨てていた。WM に
  計数用のログを入れて、クライアントメッセージが**届いていない**ことを確かめて特定。
  終了前に往復を 1 回挟んで解消（`180` も同様）。4 コアに負荷をかけて 3/3 通過
- 一括実行で「WM が起動直後に終了」がランダムに出る … 8 本の trap が lib.sh の後始末を
  潰して Xvfb を残していたのと、死にかけの旧 Xvfb に疎通確認が通る起動レース

一括実行を 19 本の時点で 2 回、23 本になってから 3 回（最後は最終ビルド）、いずれも全通過・リーク 0。

### 設計上の指摘（テストを書く過程で見つかったもの）

**250ms タイムアウトと `CF_SYNC_UNFIT` の記録が `sync.c` と `move.c` に
二重に実装されている。**

- `sync.c: sync_check_timeout()` … 全クライアントを走査する版
- `move.c: move_tick()` … ドラッグ中のクライアントだけを見る版

両方に同じ閾値（`WM_SYNC_TIMEOUT_MS`）と同じ副作用（`SYNC_STALLED` へ落とし
`CF_SYNC_UNFIT` を立てる）が書かれている。**片方だけ直すと不整合になる**。
実際、`180` を書くときに `sync.c` 側だけを無効化してテストが素通りしたことで
気づいた（`move.c` 側が代わりに動いていた）。

いまのところ挙動は同じなので害は出ていないが、
どちらかに寄せるべき。判断は Phase 5 の整理に回す。

## 5. 手動でしか確認できないもの

`docs/MANUAL-TEST.md` を参照。自動化できない理由が明確なものだけを残している。

| 項目 | 自動化できない理由 |
| --- | --- |
| 実アプリの描画（GTK / Qt / Electron / LibreOffice） | 開発環境にパッケージが無い。挙動がツールキットの版に依存する |
| トレイアイコンの**絵**が正しく出るか | アプリ側の描き方に依存する。XEmbed の配線自体は `120` で検証済み |
| RandR の再構成 | **Xvfb が RandR の変更通知を一切配送しない**（4 種すべて select したプローブで 1 件も届かないことを確認済み） |
| 日本語タイトルの見え方 | 環境の X コアフォント次第（core ビルドは best-effort）。**Xvfb 上では `075` が 2 つのフォント環境で検証している**ので、手動で見るのは実機の Xorg で同じになるかだけ |
| Win98 実物との意匠比較 | 参照画像が要る |
| OpenBSD | Phase 5 |

## 6. この表の使い方

新しい要求を SPEC に足したら、**この表に行を足してから**実装する。
行が「未」のまま残るのは構わない（§4 に優先度つきで残っている）が、
**表に存在しない要求を実装してはいけない**。
「仕様に書いたから実装したはず」を防ぐのがこの表の役目である。
