# w98wm 仕様書

Windows 98 のルック＆フィールを再現しつつ、現代のアプリケーション（GTK3/4・Qt5/6・Electron・
Firefox・Chromium 等）が正常に動作する、超軽量な X11 リパレンティング型ウィンドウマネージャ。

| 項目 | 内容 |
| --- | --- |
| 名称 | **未定**（実装後に決定。仮称 `w98wm`、§11.1 の方法で後から変更可能にする） |
| 言語 | C99（フリースタンディング寄り、C++/STL 不使用） |
| 対象カーネル | Linux（glibc / musl）、OpenBSD |
| 対象ウィンドウシステム | X11 のみ（Wayland は将来の別バイナリとして検討、本仕様の対象外） |
| プロトコル準拠 | ICCCM 2.0（実装する節は §5.1）、EWMH 1.5、Motif WM Hints、XEmbed/System Tray（Phase 4） |
| メモリ目標 | `Private_Dirty` 1 MB 未満（§9.1 の指標 A。core ビルドのみ対象・承認済） |
| ライセンス | MIT（変更可） |

## 1. 設計方針

### 1.1 三つの制約の同時達成

本プロジェクトの難しさは、通常トレードオフになる 3 つを同時に満たす点にある。

1. **見た目の忠実さ** — Windows 98 の**視覚的外観**を、可能な限りピクセル精度で再現する
   （Windows の描画コードそのものの再現ではない。基準画像の定義は §4.0）。
2. **現代アプリの動作** — EWMH/ICCCM の実装漏れは、GTK のダイアログが画面外に出る、Qt の
   全画面が効かない、Electron がリサイズでちらつく等の形で即座に露見する。準拠は必須。
3. **1 MB 未満のメモリ** — Xlib・Xft・fontconfig・cairo・GLib を一切使わないことで達成する。

この 3 つ目の制約が、以下のすべての技術選択を規定する。

#### 1.1.1 3 つの目標が実際に衝突する箇所（正直な限界）

上の 3 つは完全には両立しない。**看板に書けない部分を先に明示しておく。**
以下は実装で解決する課題ではなく、この設計を選んだ時点で確定する限界である。

| 衝突 | 実際に起きること | 本仕様の立場 |
| --- | --- | --- |
| **CSD アプリの外観** | GTK3/4 の CSD アプリ（GNOME 系、一部の Electron）は自前でタイトルバーを描くため、**Win98 の外観にならない**。§7.2 は「装飾を付けない」と規定しており、これは仕様通りの動作である | 「すべてのアプリが Win98 風になる」とは**謳わない**。SSD を使うアプリ（Qt、Firefox、xterm、多くの GTK3 アプリ）でのみ外観が一致する。`GTK_CSD=0` の案内はするが強制はできない |
| **フォントの字面** | MS Sans Serif を同梱できないため、タイトルの字面は実機と異なる。§4.0 で「グリフ形状は一致要求の対象外」と既に除外している | ピクセル一致を要求するのは**フレーム・ベベル・ボタン・配色**であり、文字そのものではない。この区別を README にも書く |
| **メモリと機能** | タスクバー・トレイ・スタートメニューを内蔵しながら 1 MB を守れるかは**未検証**（§9.1.1） | 反証されたときの削減順序を §9.1.1 に先に定めた |
| **コンポジット** | 影・半透明・滑らかなアニメーションは無い。picom と共存はするが内蔵しない | Win98 にもこれらは無いため、意匠上はむしろ正しい。ただし「現代的な見た目」を期待する層には応えない |
| **HiDPI** | 整数倍（1x / 2x）のみ。**per-monitor DPI と非整数倍スケールには対応しない** | ピクセルアートの意匠を保つための意図的な選択。混在 DPI 環境では片方のモニタで大きさが合わない |

これらは「後で直す」項目ではない。**この設計を選ぶ限り残る**ものとして受け入れる。

### 1.2 技術選択と根拠

| 領域 | 採用 | 不採用にしたもの | 根拠 |
| --- | --- | --- | --- |
| X クライアントライブラリ | **libxcb**（生の xcb + 自前ヘルパ） | Xlib | Xlib は接続時に約 200–400 KB のヒープを確保し、ロケール/XKB/リソースDBを抱え込む。xcb は薄い |
| 描画 | **xcb コアプロトコル**（PolyFillRectangle / PolyLine / **PolyText16**） | cairo, XRender, GTK | Win98 の意匠は矩形・1px 線・ベベル・水平グラデーションのみ。コア描画で完全再現できる。文字は前景のみ描く `PolyText16` を使う（理由は §4.5.4.1） |
| フォント | **X コアフォント**を既定（core ビルド）、`XFT=1` は別ビルドプロファイル（§1.4） | fontconfig + FreeType 必須構成 | コアフォントはグリフをサーバ側が持つためクライアント常駐量ゼロ。多言語表示の保証範囲は §4.5.5 |
| イベント待ち | **poll(2)** | epoll / kqueue | 2 OS 共通・fd 数が一桁のため性能差なし。移植層を薄くできる |
| 設定 | 起動時に読む key=value テキスト、パース後にバッファ解放 | GLib KeyFile, Lua, JSON | パーサ約 150 行、常駐コスト実質ゼロ |
| メモリ確保 | 固定スラブ + チャンク拡張（クライアント 64 個単位） | 汎用 malloc 依存の細切れ確保 | 断片化を避け、アイドル時のヒープを平坦に保つ |
| 依存 | §1.4 の表を参照 | xcb-util-wm(icccm/ewmh) | ICCCM/EWMH のプロパティ操作は自前実装（約 600 行）。依存とリンク時常駐を削減 |

### 1.3 非目標

- コンポジット（影・半透明・**コンポジット由来の**アニメーション）。外部コンポジタ（picom）との共存はするが、内蔵しない。
  ただし Win98 標準の**最小化/復元時のワイヤーフレーム・ズーム**（`MinAnimate` 相当）は
  対象内とする。XOR のラバーバンド矩形をタスクバーのボタンへ向けて数フレーム描くだけで
  再現でき、コンポジットを必要としない。設定 `animate.minimize`（既定 `true`）で無効化可能。
- タイル型レイアウト、スクリプト言語による拡張、テーマエンジン（配色のみ設定可能）。
- Wayland サポート。
- Win98 の**動作**の完全再現（あくまで見た目の再現 + 現代的な操作性の追加）。
- **XSMP（X セッション管理）**。セッションの保存・復元は行わない
  （`SM_CLIENT_ID` は読まないし、セッションマネージャにも接続しない）。
- **デスクトップアイコン**。ファイル管理機能は持たない。アイコンが欲しい場合は
  `_NET_WM_WINDOW_TYPE_DESKTOP` のウィンドウを出すファイラ（pcmanfm --desktop 等）に
  任せる（それが正しく最背面に置かれることは §5.2.2 で保証する）。
- **RandR を持たない古い X サーバ**でのマルチモニタ動作（§5.3）。
- Xft ビルドにおけるメモリ目標の達成（§1.4）。

### 1.4 依存ライブラリとビルドプロファイル

| ライブラリ | 区分 | 用途 |
| --- | --- | --- |
| `libxcb` | **必須** | X プロトコル |
| `libxcb-randr` | **必須** | モニタ列挙・ホットプラグ（§5.3） |
| `libxcb-sync` | **必須** | `_NET_WM_SYNC_REQUEST` のカウンタとアラーム（§7.3） |
| `libxcb-keysyms` | **必須** | キーバインドの keysym ↔ keycode 変換 |
| `libxcb-shape` | 任意 | 非矩形ウィンドウの形状追従。無ければ矩形として扱う |
| `libxcb-xfixes` | 任意 | トレイの選択監視。無ければトレイ機能を無効化 |
| `libXft` + `libfontconfig` + `libfreetype` | **Xft ビルドのみ** | アンチエイリアス描画と多言語表示 |

**ビルドプロファイルは 2 つ**。混同を避けるため明確に分離する。

| プロファイル | 構成 | メモリ目標 | 位置づけ |
| --- | --- | --- | --- |
| **core**（既定） | libxcb 系のみ。コアフォント + 内蔵フォント | §9 の目標を**適用する** | **正式サポート**。動的リンク版が基準 |
| **xft**（`make XFT=1`） | 上記 + Xft/fontconfig/FreeType | §9 の目標は**適用しない**（実測 2 MB 前後を見込む） | 正式サポート（多言語表示や HiDPI を優先する場合の選択肢）。ただし「1 MB WM」を名乗るのは core のみ |

静的リンク（`make STATIC=1`、musl）は **experimental** とする。バイナリサイズ（実測目標
約 400 KB）と実行時の `Private_Dirty` は別の指標であり、静的リンクは後者をほとんど改善しない
（共有ライブラリのテキスト領域は元々 `Private_Dirty` に計上されない）。単一バイナリ配布の
利便性のための選択肢であって、メモリ目標の達成手段ではない。

## 2. アーキテクチャ

### 2.1 プロセス構成

単一プロセス・単一スレッド・イベント駆動。子プロセスを作るのはユーザがアプリを
起動したときのみで、`posix_spawn(3)` を使う（Linux / OpenBSD 両方にある）。

```
                +----------------------------------+
                |            w98wm (1 proc)        |
   X server <-->| xcb connection (fd)              |
                |   +--- event loop (poll)         |
   SIGCHLD ---->|   +--- self-pipe                 |
                |                                  |
                |  core/     : クライアント管理     |
                |  deco/     : 装飾描画            |
                |  proto/    : ICCCM/EWMH          |
                |  shell/    : タスクバー/メニュー  |
                +----------------------------------+
```

### 2.2.1 シグナルとプロセス管理

- **SIGCHLD は `SIG_IGN` に設定する**。POSIX により、この設定下では終了した子は
  自動回収されゾンビにならない。w98wm は子の終了ステータスを一切必要としないため、
  これが最も単純で正しい。`waitpid` ループも self-pipe への SIGCHLD 通知も不要になる。
  - ただし `SIG_IGN` の設定は exec を跨いで**継承される**ため、起動したアプリ側の
    `wait()` が壊れる。`posix_spawn` の属性に `POSIX_SPAWN_SETSIGDEF` を指定して
    子側で SIGCHLD を `SIG_DFL` に戻すこと（これを忘れるとシェルスクリプト等が誤動作する）。
  - 同様に `posix_spawn` 属性で `POSIX_SPAWN_SETSIGMASK` を使い、子のシグナルマスクを空にする。
  - **`SIG_IGN` に変更したシグナルは SIGCHLD だけではない**。下記の `SIGPIPE` も
    `SIG_IGN` にしており、これも exec を跨いで継承されるため、子が起動する
    シェルパイプライン（`foo | head` 等）が `EPIPE` で正常終了できなくなる。
    **`POSIX_SPAWN_SETSIGDEF` には、WM 側で既定から変更したシグナルをすべて含める**
    （実質「SIGCHLD と SIGPIPE を `SIG_DFL` に戻す」）。
  > **`SIG_IGN` でゾンビが残るのではないか、という懸念について**：残らない。POSIX は
  > 「SIGCHLD の処理が `SIG_IGN` に設定されている場合、子プロセスは終了時にゾンビに
  > **ならない**」と明示的に規定しており、Linux と OpenBSD の双方がこの通りに実装して
  > いる。したがって `waitpid` ループも SIGCHLD 用の self-pipe も不要である。
  > w98wm は子の終了ステータスを一切必要としないため、この選択が最も単純で正しい。
  > （self-pipe + `waitpid(-1, NULL, WNOHANG)` ループでも動作はするが、
  > 同じ結果を得るために余分な状態とコードを持つことになる。）
  > なお、起動したアプリのさらに子（孫プロセス）は w98wm の子ではないため、
  > その回収はアプリ自身か `init` の責務であり、WM 側では関与しない。

- **SIGTERM / SIGINT / SIGHUP のみ self-pipe** で受ける。
  - パイプは両端とも `O_NONBLOCK` + `O_CLOEXEC`。
  - ハンドラは async-signal-safe な `write(fd, &byte, 1)` のみを行い、
    **`EAGAIN`（パイプ満杯）は無視する**。この通知は「何かシグナルが来た」という
    エッジの合体で十分であり、取りこぼしても後続の 1 バイトで検知できる。
  - 実際に来たシグナルの種別は、ハンドラ内で `volatile sig_atomic_t` のフラグに
    立てて伝える（複数種が同時に来ても各フラグで区別できる）。
  - イベントループ側ではパイプを EOF/EAGAIN まで読み切ってからフラグを処理する。
- `SIGPIPE` は `SIG_IGN`。X 接続が切れた場合は `xcb_connection_has_error()` で検知して
  クリーンアップに入る。

### 2.2.2 X エラー処理の方針

WM は本質的に「他クライアントのウィンドウがいつでも消え得る」レースの中で動く。
`MapRequest` を受けてから reparent するまでの間にウィンドウが破棄されれば
`ReparentWindow` は `BadWindow` を返す。**これは異常ではなく通常の動作条件である。**

- **エラーはイベントとして届く**。xcb では unchecked リクエストのエラーは
  `xcb_wait_for_event` / `xcb_poll_for_event` の戻り値として、`response_type == 0` の
  形で返る。イベントディスパッチャは `response_type == 0` を必ず処理すること
  （`switch` の `default` で握り潰すと、状態が壊れたまま進む）。
- **クライアントウィンドウ宛のリクエストは常にエラーを許容する**。
  `BadWindow` / `BadDrawable` / `BadMatch` を受けたら、対象クライアントを
  「既に消えたもの」として unmanage し、ログに出す以外は何もしない。**致命扱いにしない。**
- **自リソース宛のエラーは実装バグ**。自分で作った frame / GC / Pixmap / アラームに
  対するエラーは想定されないため、`-v` 時に詳細（major/minor opcode、シーケンス番号、
  リソース ID）を出力する。デバッグビルドでは abort してよい。
  **「エラーは一律すべて破棄する」という実装にはしない。** 堅牢に見えて、実際には
  自分の実装バグを永久に隠蔽し、原因不明の描画崩れとして現れるだけになる。
  クライアント宛か自リソース宛かの二分は、リクエスト発行時に対象リソース ID を
  見れば足り、シーケンス番号の追跡は不要である。
- **管理開始は原子的に検証する**。`MapRequest` から管理に入る際は、
  `GetWindowAttributes` を **checked** リクエストで発行し、リプライが取れた場合のみ
  管理を開始する（`override_redirect` の確認も同時に行える）。
  リプライが `BadWindow` なら、そのウィンドウは既に無いので黙って無視する。
- **`UnmapNotify` と `DestroyNotify` の競合**は明示的に扱う。`UnmapNotify` を受けて
  「ルートへ reparent し直してセーブセットから外す」処理に入った時点で、
  ウィンドウが既に破棄されていることがある。この経路のリクエストはすべて
  エラーを許容し（前項の方針）、`DestroyNotify` が後から来ても
  **二重に unmanage しない**よう、クライアント構造体に解放済みフラグを持つ。
- **エラーの取りこぼしを防ぐ**。エラーの多くは unchecked リクエストから遅れて届くため、
  「どのリクエストに対するエラーか」はシーケンス番号でしか分からない。
  どのクライアントの操作中に発行したかを追跡する必要はなく、上記の
  「クライアント宛は許容・自リソース宛はバグ」の二分で十分。

#### 2.3.0 確保の失敗と上限超過時の挙動（Graceful Degradation）

メモリ目標を掲げる以上、**「確保できなかったとき何が起きるか」を仕様で決めておく**。
これが未定義だと、`xterm` を 100 個起動するスクリプトのような負荷で挙動が予測不能になる。

- **チャンク 0 は BSS に静的確保する**（64 クライアント分 = 約 28 KB）。
  通常の利用（同時 64 ウィンドウ以下）では `malloc` を一度も呼ばない。
  未使用の BSS ページは書き込むまでダーティにならないため、M0（§9.1）への影響も無い。
- 65 個目以降はチャンクをヒープから確保して連結する。
- **管理数の上限を 512 とする**。これを超える、またはチャンクの確保に失敗した場合：
  - **クライアントを殺してはならない**（`KillClient` は最悪の選択。ユーザのデータが失われる）。
  - フレームを作らず、**装飾なしの非管理ウィンドウとしてそのまま `MapWindow` する**。
    アプリは使える状態を保ち、WM の管理下に入らないだけになる。
  - この状態を `-v` でログに出す。以後、管理枠が空いても遡って管理はしない
    （そのウィンドウが閉じられるまで非管理のまま）。
- タイトル（256 B 固定）・計測キャッシュ・アイコン Pixmap はすべてクライアント構造体の
  一部か固定上限を持つため、**クライアント数以外にメモリが増える経路は無い**。
  グラデーションの矩形配列（§4.4、最大 766 要素 = 約 6 KB）は描画関数のローカル領域で、
  常駐しない。
- `realloc` によるクライアント配列の再確保は**行わない**（チャンクの連結リストにするのは
  ポインタの無効化とフラグメンテーションを避けるため）。

#### 2.3.1 タイトルはキャッシュする

タイトル文字列は構造体内に**キャッシュする**（256 B 固定、超過分は切り詰め）。

当初は「描画のたびに `_NET_WM_NAME` をサーバから読んで捨てる」設計にしていたが、これは誤り
だった。`GetProperty` はリプライを伴う同期リクエストであり、`Expose` のたびにラウンド
トリップが発生する。これは §3.4.1 で自ら定めた「**描画経路にリプライを伴う同期リクエストを
置かない**」という原則に正面から違反する。しかもタイトルの変更は `PropertyNotify` で
確実に検知できるため、そもそも毎回読む必要がない。

コストは 20 ウィンドウで 5 KB、200 ウィンドウでも 51 KB。§9 の目標に対して十分小さい。
**数 KB を節約するために X サーバとの同期を描画経路に持ち込むのは、トレードとして明確に
損である。** 更新は `PropertyNotify`（`_NET_WM_NAME` / `WM_NAME`）受信時のみ。

同じ原則により、`WM_CLASS`・`_NET_WM_PID` 等の低頻度参照プロパティは
キャッシュせず必要時に読むが、**いずれも描画経路には置かない**。

**切り詰めと変換の規則**：

- 256 B に収まらないタイトルは切り詰めるが、**UTF-8 のコードポイント境界で切る**
  （バイト単位で切ると不正なシーケンスが末尾に残る）。
- 描画は `PolyText16`（UCS-2）で行う（`ImageText16` は使えない。理由は §4.5.4.1）。
  1 つのテキストアイテムに入るのは**最大 254 グリフ**（長さ 255 はフォント切替
  アイテムの標識として予約されている）。超える場合はアイテムを分割する。
- UCS-2 に変換できない BMP 外のコードポイント（絵文字など、UTF-8 で 4 バイト）は
  **U+FFFD に置換**する。サロゲートペアには分解しない（コアフォントはサロゲートを
  解釈しないため、分解すると意味のない 2 グリフになる）。
- 不正な UTF-8 シーケンスは U+FFFD 1 個に置換して読み飛ばす
  （`_NET_WM_NAME` は UTF-8 を名乗るが、実際に壊れた値を設定するアプリは存在する）。
  デコーダは**不正バイトに遭遇しても必ず 1 バイト以上進む**こと（進まない実装を書くと
  無限ループになる）。
- **制御文字と双方向テキスト制御文字を除去する**。具体的には C0（U+0000–U+001F）、
  U+007F、C1（U+0080–U+009F）、および双方向オーバーライド類
  （U+202A–U+202E、U+2066–U+2069）を U+FFFD に置換するか削除する。
  改行を含むタイトルでキャプションの描画が崩れる、RTL オーバーライドで表示順が
  逆転して他ウィンドウになりすます、といった問題を防ぐ。
  **サニタイズはプロパティ受信直後に 1 回だけ行い、以後は安全な文字列として扱う。**
- `_NET_WM_NAME` が無い場合は `WM_NAME` を読む。こちらは Latin-1 として解釈する
  （ICCCM の `STRING` 型は ISO 8859-1）。`COMPOUND_TEXT` 型の場合は変換せず、
  ASCII 範囲のみ抽出する（完全な COMPOUND_TEXT デコーダは持たない）。

## 3. ウィンドウ管理仕様

### 3.1 フレーム構造

各クライアントは 1 枚の `frame` ウィンドウ（`InputOutput`, backing なし）に reparent される。
子ウィンドウは装飾分だけオフセットして配置。ボタン等の当たり判定はフレーム上の座標計算で行い、
サブウィンドウは作らない（ウィンドウ数を最小化するため）。

```
frame
 +-- borders (4px, 描画のみ)
 +-- caption (18px, 描画のみ)
 |     +-- icon(16x16) | title text | [_][□][X]  ← 座標計算による当たり判定
 +-- win (アプリのウィンドウ)
```

#### 3.1.0 reparent 時のクライアント属性の変更

- **クライアントの `border_width` を 0 にする**（ICCCM の要求）。`xterm` は既定で
  `border_width = 1` を持っており、0 にしないと装飾の内側に意図しない枠が出る。
  元の値は保存しておき、**unmanage 時に復元する**。
- ジオメトリ計算では、`ConfigureRequest` が指定する `border_width` も考慮する
  （クライアントが後から変更してくることがある）。
- イベントマスクを設定し（`PropertyChange` / `StructureNotify` 等）、
  unmanage 時に元へ戻す。

#### 3.1.1 セーブセット（必須・これが無いと §10-7 は達成できない）

**reparent する直前に `ChangeSaveSet(INSERT)` でクライアントウィンドウをセーブセットに
登録し、管理を解除する時（Withdrawn 遷移・WM 終了時）に `DELETE` する。**

理由：X サーバはクライアント（＝ここでは w98wm）の接続が切れると、そのクライアントが
作ったリソースをすべて破棄する。frame ウィンドウも破棄され、**`DestroyWindow` は子孫を
再帰的に破棄する**ため、reparent されたアプリのウィンドウごと消滅する。
セーブセットに登録されたウィンドウだけは、接続断時にサーバが自動的にルートの子へ
戻して再マップしてくれる。これが「WM が落ちてもアプリが生き残る」唯一の仕組みである。

- 正常終了時に自前でルートへ reparent し直す処理（§3.1 の従来の記述）は、
  **異常終了には効かない**。`kill -9`・セグフォルト・X 接続断ではそのコードは走らない。
- セーブセットからの復帰時、ウィンドウはフレーム内での相対位置のままルート直下に置かれる。
  位置ずれを避けるため、reparent 時のオフセットを考慮して座標を戻すのは次の WM の責務
  （ICCCM が想定する動作であり、ここでは追わない）。
- セーブセットは**マップされているウィンドウにのみ有効**。unmap 済みのウィンドウは
  接続断時に復帰しないため、最小化中のウィンドウについては別途 §3.3 の `WM_STATE` に
  従って次の WM が復元する。

`ChangeSaveSet` は仕様全体で唯一「WM が落ちたときの安全網」であり、実装漏れが起きても
通常操作では一切表面化しない（テストしない限り気づけない）。**Phase 1 の最初に入れる。**

### 3.2 装飾の有無

以下の場合は装飾なし（フレームは作るが borders/caption を 0 にする、もしくは reparent しない）：

- `_MOTIF_WM_HINTS` で `MWM_DECOR_ALL` が無効、または decorations = 0
- `_NET_WM_WINDOW_TYPE` が `DESKTOP` / `DOCK` / `SPLASH` / `TOOLTIP` / `DND` /
  `DROPDOWN_MENU` / `POPUP_MENU` / `COMBO` / `NOTIFICATION`
- `override_redirect` が立っている（そもそも管理対象外）
- `_NET_WM_STATE_FULLSCREEN` 中
- `_GTK_FRAME_EXTENTS` を持つ CSD アプリ（GTK3/4）※§7.2

### 3.3 状態遷移（ICCCM 4.1.4）

`Withdrawn → Normal → Iconic` を `WM_STATE` プロパティで正しく通知する。
`Iconic`（最小化）は子をアンマップし frame もアンマップ、`_NET_WM_STATE_HIDDEN` を立てる。
タスクバーからの復帰、`_NET_ACTIVE_WINDOW` クライアントメッセージでの復帰に対応。

### 3.4 移動・リサイズ

- タイトルバードラッグで移動。既定は**ライブ移動**（Win98 の「ドラッグ中にウィンドウの内容を
  表示する」ON 相当）。設定 `drag.outline = true` で Win95 風のラバーバンド枠に切替可能（§8）。
- ボーダー 8 方向ドラッグでリサイズ。`WM_NORMAL_HINTS` の
  `min/max size`, `resize increments`, `base size`, `aspect ratio`, `win_gravity` を厳密に適用
  （端末エミュレータの文字単位リサイズが正しく効くこと）。
- `Alt + 左ドラッグ` = 移動、`Alt + 右ドラッグ` = リサイズ（現代的な追加操作）。
- **カーソル形状は内蔵のビットマップから作る**（§4.9）。フレーム上のポインタ位置に
  応じて、8 方向のリサイズカーソル・通常の矢印・移動カーソルを設定する（§4.7）。
- `_NET_WM_MOVERESIZE` クライアントメッセージ経由の移動/リサイズに対応（GTK CSD アプリの
  タイトルバードラッグがこれを使う）。
- **スナップ**：画面端・他ウィンドウ端への吸着（既定 8px）。Aero Snap 相当の
  「上端で最大化 / 左右端で半分」は既定 OFF（Win98 に無いため）、設定で有効化可能。

#### 3.3.1 新規ウィンドウの初期配置

仕様から丸ごと抜けていた項目。決めないと実装時に必ず迷い、`xterm -geometry` や
位置を自前で復元するアプリが壊れる。優先順位は上から順に評価する。

1. **`WM_NORMAL_HINTS` の `USPosition`**（ユーザが明示指定した位置。`-geometry` 等）が
   立っていれば、**その位置を無条件で尊重する**（作業領域外でもクランプしない）。
2. **`PPosition`**（アプリが指定した位置）が立っていれば尊重するが、4. のクランプは適用する。
   ただし位置が `(0,0)` の場合は「指定なし」として扱う（`PPosition` を立てたまま
   座標を設定しないアプリが多いため）。
3. 位置指定が無い場合：
   - **`DIALOG` 型または `WM_TRANSIENT_FOR` を持つ**ウィンドウは、**親の可視領域の中央**に
     配置する（親が無い・親が画面外なら、ポインタのあるモニタの中央）。
   - **`SPLASH`** はモニタ中央。
   - それ以外（`NORMAL`）は **Win98 流のカスケード配置**。最後に配置した位置から
     `(caption_height, caption_height)` = (18, 18) ずつずらす。作業領域の右下に達したら
     左上（作業領域の原点 + オフセット）に戻り、開始オフセットを 1 段ずらす。
     カスケードの原点はモニタごとに独立に持つ。
4. **クランプ**（1. を除く全経路に適用）：
   - タイトルバーが作業領域内に**最低 1 箇所は残る**ようにする（完全に画面外に置かない）。
   - ウィンドウが作業領域より大きい場合は、サイズを縮めず**左上を作業領域の原点に合わせる**
     （縮めると `WM_NORMAL_HINTS` の最小サイズや増分と衝突するため）。
5. 配置の基準となるモニタは、1./2. では指定座標が属するモニタ、3. ではポインタのある
   モニタ（`_NET_WM_DESKTOP` や親の所属が判っていればそちらを優先）。
6. CSD ウィンドウでは、これらの判定に可視矩形 `V` を使う（§7.2）。

#### 3.4.1 ドラッグ中のフレームペーシング（必須）

ドラッグ中に `MotionNotify` 1 件ごとに `ConfigureWindow` を送る素朴な実装は、低速な
リモート X（実際によくある用途）や重量級クライアントで破綻する。以下を**実装上の必須要件**
とする。

1. **モーションの合体**：`MotionNotify` は毎回処理せず、イベントキューを空になるまで
   ドレインして**最後の 1 件だけ**を使う（`xcb_poll_for_queued_event` でループ）。
   ポインタは `PointerMotionHint` 付きで grab し、必要時に `QueryPointer` で現在位置を取る
   方式も併用できるようにする（サーバ→WM 方向のイベント量そのものを減らせる）。
2. **レート上限**：位置/サイズの反映は **16 ms（約 60 Hz）以上の間隔**を空ける。
   直前の反映からの経過時間が足りなければ、`poll(2)` のタイムアウトを残り時間に設定して
   次のループで反映する（タイマスレッドもタイマ fd も使わない）。
3. **未確定リクエストは 1 つまで（ドラッグ中のみ）**：リサイズ時は §7.3 の同期カウンタが
   返るまで次の `ConfigureWindow` を送らない。移動のみの場合はカウンタを使わず
   2. のレート上限で制御する。
4. **ドロップ時の確定**：ボタン解放時は 2. と 3. の抑制を解除し、最終ジオメトリを必ず
   1 回送る。同期カウンタとの整合は §7.3 の「ボタン解放時の扱い」で規定する
   （新しい target を採番して即送る）。

補足：`ConfigureWindow` はリプライを伴わない非同期リクエストであり、1 回ごとにサーバとの
往復（ラウンドトリップ）が発生するわけではない。ここでの実際のボトルネックは
(a) 送信バイト量とサーバ側のキュー滞留、(b) クライアント側の再描画コストの 2 つであり、
対策は上記のイベント合体とレート制御になる。ラウンドトリップを避ける設計（リプライを
待つ同期リクエストを描画経路に置かない）は別途原則として守る。

### 3.5 最大化・全画面

- 最大化は**モニタ別作業領域**（§3.5.2）に対して行う。対象モニタは、
  ウィンドウの中心が属するモニタ（CSD の場合は `W` ではなく可視矩形 `V` の中心。§7.2）。
  **中心がどのモニタにも属さない場合**（ウィンドウが画面外にはみ出している、
  モニタ配置に隙間がある）は、**ウィンドウとの交差面積が最大のモニタ**を選ぶ。
  交差が皆無ならポインタのあるモニタ。
- 全画面（`_NET_WM_STATE_FULLSCREEN`）はモニタ全域、装飾なし、strut 無視。
  スタッキングは §3.7.1（フォーカス時のみ最上層）。
  `_NET_WM_FULLSCREEN_MONITORS` に対応（複数モニタ跨ぎ）。
- 動画プレイヤ・ブラウザの全画面が確実に効くことは受け入れ条件（§10）。

#### 3.5.1 復元ジオメトリの保持（最大化と全画面は独立に重なる）

最大化したウィンドウをブラウザで F11 して全画面にし、全画面を解除したら**最大化状態に
戻り**、さらに最大化を解除したら元の位置に戻る——この 2 段の復元が必要なため、
保存領域を 1 つにしてはならない。

- `restore` は**非最大化かつ非全画面のジオメトリ**のみを保持する。
  最大化や全画面への遷移で**上書きしない**。更新されるのは、通常状態でユーザが
  移動・リサイズしたときだけ。
- `pre_fs` / `pre_fs_states` は全画面に入る直前のジオメトリと最大化状態を保持する。
  全画面を解除したらここへ戻す。
- **`SHADED` との組み合わせ**：シェード中に最大化した場合、シェードを維持したまま
  幅だけ最大化し、`restore` の `height` は保持する（シェード解除時に正しい高さに戻る）。
  シェード中に全画面を要求されたらシェードを解除してから全画面にする。
- **最大化ジオメトリは保存しない**。常にモニタ別作業領域（§3.5.2）から導出する。
  これによりモニタ構成が変わっても最大化状態が追従する。
- `MAXIMIZED_VERT` と `MAXIMIZED_HORZ` は独立した状態である（EWMH）。
  片軸ずつの適用・解除に対応するため、復元は**軸ごとに `restore` の該当成分から行う**
  （垂直最大化を解除したら `y` と `height` だけ `restore` から戻し、`x` と `width` は
  現在値を維持する）。
- ウィンドウがマップされた時点で `restore` を初期ジオメトリで初期化する
  （初期状態で最大化を要求されるアプリのために、これを先に行う）。

#### 3.5.2 strut からモニタ別作業領域を求める規則

`_NET_WM_STRUT_PARTIAL` は**ルートスクリーンの外周 4 辺**からの距離で表現される
一方、最大化はモニタ単位で行う。素朴に全モニタへ同じ strut を適用すると、
解像度の違う 2 画面などで一方の最大化領域が不当に削れる。規則を明示する。

- strut は、**その辺に接しているモニタにのみ適用する**。「接している」とは、
  モニタの当該辺の座標がルートスクリーンの当該辺と一致することをいう。
- さらに `_NET_WM_STRUT_PARTIAL` の `start` / `end` 区間と、モニタの当該辺の区間が
  **交差する場合のみ**適用する（区間指定のないレガシーな `_NET_WM_STRUT` は
  辺全体に及ぶものとして扱う）。
- 適用した結果、モニタの作業領域の幅または高さが 0 以下になる strut は**無視する**
  （壊れたパネルによる作業領域の消滅を防ぐ）。
- 複数の strut が同じ辺に適用される場合は最大値を採る。

**用語の分離**（これまで両方の意味で `_NET_WORKAREA` を使っていたため）：

| 用語 | 意味 |
| --- | --- |
| `_NET_WORKAREA`（ルートプロパティ） | EWMH が定義するデスクトップごと 1 個の矩形。**全モニタの外接矩形から、外周 4 辺に接する strut を引いた 1 矩形**として算出する（EWMH は 1 矩形しか表現できないため、これが慣例）。**外部クライアントへの通知用**であり、pager 等が読む。w98wm 自身の配置計算には使わない |
| **モニタ別作業領域**（内部値） | モニタごとに保持する矩形。**最大化・スナップ・ウィンドウ配置は常にこちらを使う** |

### 3.6 フォーカス

- 既定は **click-to-focus**、設定 `focus.mode = sloppy` で sloppy focus（§8）。
- `WM_HINTS.input` と `WM_TAKE_FOCUS` を組み合わせた ICCCM 準拠のフォーカス付与
  （Globally Active クライアント＝Java/Qt の一部が正しく動くために必須）。
- `_NET_ACTIVE_WINDOW` の source indication を尊重（pager からの要求は許可、アプリからの
  自己アクティブ化は `_NET_WM_USER_TIME` で判定し、古い場合は
  `_NET_WM_STATE_DEMANDS_ATTENTION`（＝タスクバーボタン点滅）に落とす）。
- MRU 順のフォーカス履歴を保持し、ウィンドウ破棄時に適切な次のウィンドウへ移す。
- **フォーカスを与える先が無くなったとき**（最後のウィンドウが閉じた、全ウィンドウが
  別デスクトップにある等）は、`PointerRoot` に戻してはならない。戻すと click-to-focus
  設定なのにポインタ位置で入力先が変わる挙動が漏れる。
  **起動時に 1×1 の `InputOnly` ダミーウィンドウを作っておき、行き先が無いときは
  そこへ `SetInputFocus` する**（`_NET_ACTIVE_WINDOW` は `None` にする）。

### 3.7 スタッキング

#### 3.7.1 レイヤ

EWMH の推奨スタッキング順に従い、下から順に以下の 6 層。

| # | レイヤ | 対象 |
| --- | --- | --- |
| 0 | `desktop` | `_NET_WM_WINDOW_TYPE_DESKTOP` |
| 1 | `below` | `_NET_WM_STATE_BELOW` |
| 2 | `normal` | 上記以外のすべて（**フォーカスされていない全画面ウィンドウを含む**） |
| 3 | `dock` | `_NET_WM_WINDOW_TYPE_DOCK`、`_NET_WM_STATE_ABOVE` |
| 4 | `above` | 一時的なポップアップ（`TOOLTIP` / `NOTIFICATION` / メニュー類） |
| 5 | `fullscreen` | **フォーカスを保持している**全画面ウィンドウのみ（下記の定義） |

**全画面 ≠ ABOVE**。EWMH は最上層に置くのを「フォーカスされた全画面ウィンドウ」に
限定している。全画面ウィンドウがフォーカスを失ったら `normal` に落とすこと。これを
怠って全画面を常時最上層に置くと、パネル・ポップアップ・他アプリのダイアログが
全画面ウィンドウの裏に隠れて操作不能になる（この種の不具合の典型的な原因）。

**ただし「フォーカスされている」は自分自身に限らない。** 全画面の動画プレイヤが設定
ダイアログ（transient）を開くとフォーカスはダイアログへ移るが、このとき全画面本体を
`normal` に落とすと、`dock` 層のタスクバーが全画面の上に被さって表示が壊れる。
そこで条件を次のように定義する。

> レイヤ 5 に置くのは、**フォーカスウィンドウが当該全画面ウィンドウ自身であるか、
> またはその transient チェーン（§3.7.2 と同じ 16 段の探索）に属する場合**。

§3.7.2 の `effective_layer` は子を親の層へ引き上げる規則であって、親を維持する規則では
ないため、この条件を別途置かないと穴が残る。

#### 3.7.2 transient チェーン

レイヤと transient 関係が競合した場合、**レイヤ決定が先、transient は同一レイヤ内での
順序付け**とする。ただし親より低い層に沈まないよう、実効レイヤは以下で決める。

```
effective_layer(c) = max(layer_of(c), effective_layer(parent_of(c)))
```

- `transient_for` の子は、実効レイヤが同じ親のすぐ上に置く。
- チェーン（親 → transient → transient）を再帰的に辿る。
  **`transient_for` のループ（A→B→A や自己参照）は実在する**（壊れたアプリ、
  および悪意ある入力）。辿る深さを 16 段に制限し、既訪問集合で循環を検出して打ち切る。
  ここを無防備に書くと無限ループでハングする。
- `transient_for` がルートウィンドウを指す場合は、ICCCM に従い
  「そのウィンドウグループ全体に対する transient」として扱う（グループ内の最前面の上へ）。
- 親が最小化されたとき、その transient も併せて最小化する。逆に transient が
  `_NET_WM_STATE_MODAL` の場合、親をアクティブ化しようとしたら modal 側を前面に出して
  フォーカスを与える（親は入力を受け付けたままでよい。入力の遮断はアプリ側の責務）。
- `_NET_CLIENT_LIST_STACKING` は最終的な実スタック順で毎回更新する。

### 3.8 仮想デスクトップ

Win98 に仮想デスクトップは無いため既定 1 面。ただし EWMH の pager が正しく動くよう
`_NET_NUMBER_OF_DESKTOPS` 等は完全実装し、設定で 1–16 面まで増やせる（増やした場合のみ
タスクバー右にデスクトップ切替が現れる）。

**切替の実装方式**（Phase 1 のアンマップ処理に影響するため、実装前に確定させる）：

- 切替は **frame ウィンドウのアンマップ / マップ**で行う（別の座標へ退避する方式は
  採らない。座標退避はウィンドウが `_NET_MOVERESIZE_WINDOW` 等で動かされたときに
  破綻する）。
- 非表示面のウィンドウは **`WM_STATE` を `Normal` のまま**保つ。
  `_NET_WM_STATE_HIDDEN` は**立てない**。これは最小化（Iconic）と区別するためで、
  タスクバーやタスクスイッチャは「最小化されている」と「別のデスクトップにある」を
  別の状態として表示する。
- `_NET_WM_STATE_STICKY` のウィンドウ、および `_NET_WM_DESKTOP` が `0xFFFFFFFF`
  のウィンドウは全面に表示し、切替時にアンマップしない。
- **WM 起因の `UnmapNotify` はすべて同一のカウンタで無視する**。発生源は次の 3 つで、
  Phase 1 のカウンタ設計にこの一覧を含めておくこと（後から増やすと必ず壊れる）：
  1. reparent に伴う自動的なアンマップ
  2. 最小化（Iconic 遷移）
  3. **デスクトップ切替による非表示化**
- 切替時のフォーカスは、切替先デスクトップの MRU 履歴の先頭へ移す。
  該当が無ければルートへ戻す（`_NET_ACTIVE_WINDOW` は `None` にする）。

## 4. 外観仕様（Windows 98 再現）

### 4.0 再現の基準

「ピクセル精度で再現する」の対象を明確にしておく。Win98 の描画は色深度・テーマ・
画面 DPI で変わるため、基準を固定しないと検証できない。

- **基準環境**：Windows 98 SE / 96 dpi / 32bit カラー / 配色「Windows スタンダード」/
  大きいフォント無効。この条件のスクリーンショットを `tests/reference/` に置く。
- **一致を要求する範囲**：フレーム・ベベル・キャプションバー・キャプションボタン・
  メニュー・タスクバーの**幾何と色**。これらは 1 ピクセルの差も許容しない。
- **一致を要求しない範囲**：フォントのグリフ形状（MS Sans Serif を同梱できないため）と、
  それに伴う文字位置の微差。

| 種別 | 外側 TL / BR | 内側 TL / BR | 用途 |

```
--- ここからキャプション/クライアント領域 ---
```

### 4.4 タイトルバー

- 背景は左→右の水平グラデーション。**固定分割数ではなく、色が実際に変化する境界で
  分割する**。境界は **3 チャネルそれぞれの変化位置の和集合**として求める。
  色が変わるのは「いずれかのチャネルが変わる位置」であり、各チャネルの変化位置は
  一般に一致しないため、段数の上限は
  **`ΔR + ΔG + ΔB + 1`**（既定配色 `#000080` → `#1084D0` では
  `16 + 132 + 80 + 1` = **229 段**）となる。
  配色は設定で変更可能（§4.1）なので、任意の色に対する上限
  `255 × 3 + 1 = 766` 段を前提にバッファを確保する（一時領域で約 6 KB）。
  この境界で `PolyFillRectangle` の矩形列を作れば、
  **本仕様が定める線形補間と完全に同一の結果**が、幅に依存しない有界なリクエスト量で得られる。

  > **補間規則そのものは暫定である。** ここで保証しているのは「矩形分割が線形補間と
  > 一致すること」であって、「Win98 の GDI が線形補間を使っていること」ではない。
  > 実機の補間アルゴリズム（丸めの方向、端点の扱い、色深度ごとのディザ）は
  > 未検証であり、§4.0 の基準スクリーンショットとの厳密比較で確定させる。
  > 比較の結果ずれていた場合、**変更するのは補間規則であって分割方式ではない**
  > （分割方式は任意の単調な補間規則に対して有効）。この検証は Phase 2 の完了条件に含む。

  > 当初「最大 133 段」と書いていたのは誤りだった。133 は変化量が最大のチャネル（G）の
  > 段数であり、これは段数の**下限**（全チャネルの変化位置が最大限重なった場合）である。
  > 上限と取り違えていた。133 要素で配列を確保するとバッファ溢れか描画の打ち切りが起き、
  > §4.0 のピクセル一致要求を満たせない。
  > なお「32 分割」という当初の近似案も §4.0 を満たさないため撤回済み。
- アイコン：詳細は §4.4.1。
- タイトル文字：フォントの決定と失敗時の挙動は §4.5 に規定する。
  収まらない場合は末尾を `...` で省略。
- ボタン：右から `[X]` `[□]` `[_]`。`WM_NORMAL_HINTS` でリサイズ不可なら最大化ボタンを
  無効表示（グレイのエンボス）。`_NET_WM_ALLOWED_ACTIONS` に反映。
- **ダイアログのボタン構成**：`_NET_WM_WINDOW_TYPE_DIALOG` である、**または**
  `WM_TRANSIENT_FOR` を持つウィンドウは **`[X]` のみ**（最小化・最大化とも表示しない）。
  §5.2.2 の表の DIALOG 行もこの規定に従う。
  - Win98 のダイアログにある `[?]`（コンテキストヘルプ）ボタンは**実装しない**。
    Windows では `WS_EX_CONTEXTHELP` に由来するが、**X には対応する標準の伝達手段が
    存在しない**。当初「`WM_HINTS` 次第で `[?]`」と書いていたのは誤りで、ICCCM の
    `WM_HINTS` にヘルプボタンに相当するフィールドは無い
    （`input` / `initial_state` / `icon_*` / `window_group` / `urgency` のみ）。
- ダブルクリックで最大化/復元、右クリックでウィンドウメニュー。

#### 4.4.1 アイコンの取得とサーバ側リソースの上限

クライアント側 RAM を減らす代わりに X サーバ側リソースを使う設計なので、**上限を仕様で
縛る**。`_NET_WM_ICON` は数 MB になり得る（256×256 の 1 枚だけで 256 KB）ため、無防備に
読むとクライアント側のメモリ目標も一時的に破る。

- **プロパティは分割して読む**。`GetProperty` の `long_offset` / `long_length` を使い、
  まず先頭の 2 ワード（幅・高さ）だけを読んでアイコン一覧を走査し、**採用する 1 枚の
  ピクセルデータだけ**を後から読む。プロパティ全体を一度にメモリへ載せない。
- **採用規則**：16×16 が存在すればそれを使う。無ければ 16×16 以上で最小のものを選び、
  最近傍で 16×16 に縮小する。**一辺 256 を超えるエントリは走査対象から除外**する。
  プロパティ全体が 4 MB を超える場合はアイコン無しとして扱う（防御的上限）。
- **保持は 1 クライアントあたり Pixmap 1 枚 + マスク 1 枚（16×16）のみ**。
  合計でも 1 枚あたり約 1.5 KB のサーバ側リソースに収まる。
- **アイコン変更時（`PropertyNotify`）は、新しい Pixmap を作ってから古い方を即座に
  `FreePixmap` する**。頻繁にアイコンを差し替えるアプリ（進捗表示など）でサーバ側の
  リソースが単調増加しないこと。クライアント破棄時も同様に解放する。
- 元の ARGB データはクライアント側に一切保持しない（変換用の一時バッファのみ、
  16×16×4 = 1 KB のスタック領域で足りる）。
- **分割読みの最中にプロパティが差し替わるレースを検出する**。2 回以上の `GetProperty`
  の間にクライアントがアイコンを差し替えると（進捗表示のように頻繁に差し替えるアプリが
  まさにこれに該当する）、幅・高さと食い違う長さのデータを画像として解釈してしまう。
  各リプライの全長（`value_len + bytes_after`）を初回の値と突き合わせ、
  不一致なら最初から読み直す。リトライは 2 回までとし、超えたらアイコン無しとして扱う。
- `_NET_WM_ICON` が無ければ `WM_HINTS.icon_pixmap` / `icon_mask` を使う。
  ただし**そのまま参照するだけでは済まない**：ICCCM 上このピクスマップは任意サイズで、
  慣習的に深度 1 のことが多い。深度が画面と異なる Drawable に `CopyArea` すると
  `BadMatch` になるため、**深度 1 なら `CopyPlane`、画面深度と一致するなら `CopyArea`、
  それ以外の深度は無視**する。サイズが 16×16 でない場合は `_NET_WM_ICON` と同様に
  16×16 へ縮小した Pixmap を自前で作る。
- 上記のいずれも無ければ内蔵の既定アイコンを描く。
- M20 の測定時に `xrestop` でサーバ側リソースも記録し、ウィンドウ数に対して線形に
  収まっていることを確認する（§9.1）。

### 4.5 フォントの解決とフォールバック

コアフォントは近年インストールされていない環境が普通にあるため（`font-misc-misc` や
`xorg-fonts-*` が既定で入らないディストリ、フォントパスが空の X サーバ）、
**フォントの取得に失敗しても w98wm は必ず起動する**。フォント関連の失敗は fatal error に
しない。ただし「何が描けるか」の保証範囲は限定される（§4.5.5）。

#### 4.5.1 フォールバックチェーン

起動時に上から順に試し、最初に成功したものを採用する。採用結果は `-v` 時にログへ出力し、
`w98wm --print-font` でも確認できる。

| # | 候補 | 備考 |
| --- | --- | --- |
| 1 | 設定ファイルの `font`（指定時のみ） | 失敗時は警告のみ出して次へ（起動は継続） |
| 2 | `-*-tahoma-medium-r-normal--11-*-*-*-p-*-iso10646-1` | 存在すれば最も近い（Win98 の一部 UI で実際に使われた書体） |
| 3 | `-*-helvetica-medium-r-normal--11-*-*-*-p-*-iso10646-1` | 広く存在する近似。MS Sans Serif そのものではないが、11px ビットマップの字面としては実用上十分近い |
| 4 | `-*-helvetica-medium-r-normal--11-*-*-*-p-*-iso8859-1` | 同上（Latin-1 のみ） |
| 4b | `-*-lucida-medium-r-normal-sans-11-*-*-*-p-*-iso10646-1` | |
| 5 | `-misc-fixed-medium-r-normal--13-*-*-*-*-*-iso10646-1` | `font-misc-misc`。等幅だが可読 |
| 6 | `-misc-fixed-medium-r-normal--13-*-*-*-*-*-iso8859-1` | |
| 7 | `-*-*-medium-r-normal--11-*-*-*-*-*-iso10646-1` から順に `--12-` `--13-` `--10-` `--14-` の 5 パターンを個別に照会 | サイズだけ合わせた総当たり |
| 8 | `fixed` | 事実上すべての X サーバが持つ別名 |
| 9 | **内蔵ビットマップフォント** | §4.5.3。X サーバにフォントが 1 つも無い場合の最終手段 |

候補の照会には `ListFontsWithInfo`（`xcb_list_fonts_with_info`）を使い、**マッチが
1 件以上あることを確認してから** `OpenFont` する。`ListFonts` ではなく
`ListFontsWithInfo` を使うのは、同時に得られる FONTINFO（文字コード範囲・
`default_char`・`max_bounds`）を §4.5.2 と §4.5.4 で使うためである。
このリプライには per-char メトリクスの配列は含まれないため、§4.5.2 の
`QueryFont` 禁止に抵触しない。

> **パターン構文の注意**：X プロトコルのフォント名マッチングで使えるワイルドカードは
> `*`（任意長）と `?`（1 文字）**のみ**である。`[0-4]` のような文字クラスは
> **存在しない**（`[` はリテラルとして扱われ、永久に 0 件マッチになる）。
> 複数サイズを試したい場合は、パターンを分けて順に照会すること。

> **実装上の落とし穴**：xcb の `xcb_open_font()` は unchecked リクエストであり、存在しない
> フォント名を渡してもその場では失敗せず、後続の描画で `BadFont` が非同期に返る。必ず
> `xcb_open_font_checked()` + `xcb_request_check()` で同期的に確認すること。ここを誤ると
> 「起動はするが文字だけ出ない」「無関係な描画が壊れる」という追いにくい不具合になる。

#### 4.5.2 文字幅の計測（メモリ上の注意点）

`QueryFont` のリプライには**フォントの全文字の per-char メトリクス**が含まれる。
ISO10646 の大きなフォントでは 12 B × 数万文字 ＝ **数百 KB のリプライ**になり、
一時的とはいえ 1 MB 目標を単独で脅かす。したがって：

- `max_byte1 == 0`（＝ 256 文字以下の 8bit フォント）のときのみ `QueryFont` を使い、
  ASCII 範囲の幅表（96 × 2 B）と `max_bounds` を控えてリプライは即座に解放する。
- 16bit フォント（iso10646-1 等）では `QueryFont` を**呼ばない**。文字列幅は
  `QueryTextExtents`（`xcb_query_text_extents`）で必要時のみ取得する。
- 省略（`...`）位置の決定に二分探索で何度も往復しない。`max_bounds.character_width` から
  収まる文字数を見積もり、**追加の往復は最大 2 回**に制限する（1 回目で超過なら見積もりを
  縮めて 2 回目、それでも超過なら安全側に切り詰める）。
- **この `max_bounds` と `font_ascent` / `font_descent` は `ListFontsWithInfo` の
  リプライから取る**（§4.5.1）。`QueryFont` を禁止した以上、16bit フォントでの
  メトリクス取得手段はこれしかない。フォント選択時に控えておき、以後は再取得しない。

#### 4.5.2.1 計測結果はキャッシュする（`Expose` で往復してはならない）

**計測を行うのはタイトル変更時（`PropertyNotify`）とキャプション幅の変化時
（リサイズ・装飾の変化）だけ**とし、結果を `struct client` にキャッシュする。
`Expose` ハンドラは**一切ラウンドトリップを発生させない**（キャッシュされた
「描画するグリフ数」と「省略記号の有無」を使って描くだけ）。

```c
uint8_t  draw_glyphs;   /* 実際に描画する UCS-2 グリフ数 */
uint8_t  draw_ellipsis; /* 末尾に "..." を付けるか */
uint16_t caption_w_at_measure;  /* 計測時のキャプション幅（変化検出用） */
```

当初は「タイトル描画は `Expose`・タイトル変更・フォーカス変化時のみで頻度が低いため、
往復コストは許容できる」としていたが、**これは誤りだった**。既定のライブ移動（§3.4）で
ウィンドウを他のウィンドウの上でドラッグすると、コンポジタ非使用の X では
**下にあるウィンドウの露出領域ごとに `Expose` が発生する**。60 Hz でドラッグすれば
下にあるウィンドウ群のタイトルが毎フレーム再描画され、そのたびに同期往復が走る。
§3.4.1 が明示的に想定する 30 ms RTT のリモート X では毎秒数百往復となり、
ドラッグ側をいくらペーシングしても画面全体が止まる。

これは §2.3.1 で撤回した「描画のたびにプロパティを読む」設計と**同型の欠陥**であり、
§3.4.1 の「描画経路にリプライを伴う同期リクエストを置かない」という原則への違反である。
`Expose` は低頻度ではない。

#### 4.5.3 内蔵フォント

候補 1–8 がすべて失敗した場合に使う、8×11 相当のプロポーショナルビットマップ
（ASCII + Latin-1、224 グリフ、幅表込みで約 3 KB を `.rodata` に持つ）。
起動時に 1bit の Pixmap アトラス 1 枚をサーバ側に作り、描画は
**`FillStippled` + `PolyFillRectangle`**（アトラスを GC のステップルにし、
`tile-stipple-origin` をずらして目的のセルを重ねる）で行う。
クライアント側の常駐増加は幅表のみ。

> **`CopyPlane` を使ってはならない（当初の記述の訂正）。**
> 深度 1 → 深度 N の `CopyPlane` は、**ビットが 0 の画素を GC の背景色で塗る**。
> つまりコピー矩形の全面が背景色で埋まり、文字の背後に単色の箱が出る。
> これは §4.5.4.1 で `ImageText16` を禁止したのと**まったく同じ欠陥**であり、
> グラデーションのタイトルバー上で §4.0 のピクセル一致要求を破る。
> `FillStippled` なら 1 のビットだけが塗られ、背景に触れない。
> 当初 §4.5.3 に「`CopyPlane` で行う」と書いていたのは、§4.5.4.1 と
> 矛盾する誤りだった。

内蔵フォントは Latin-1 のみのため、この段階に落ちた場合、日本語等のタイトルは
豆腐（□）になる。その旨を起動時に一度だけ警告し、対処（フォントパッケージの導入、
または `XFT=1` ビルド）を案内する。

#### 4.5.4 CJK 補助フォント

日本語・中国語・韓国語のタイトルは、採用したコアフォントにグリフが無い場合がある
（例：`helvetica` を採用したケース）。Xlib の `XCreateFontSet` に相当する仕組みを
最小限で自前実装する：

- プライマリフォントに加えて **補助フォントを 1 つだけ** 開く
  （既定候補：`-*-*-medium-r-normal--14-*-*-*-c-*-jisx0208.1983-0`、
  `-misc-fixed-medium-r-normal-ja-*`、`-*-*-*-*-*-*-14-*-*-*-*-*-iso10646-1`）。

**どちらのフォントで描くかは、文字コードの範囲で判定する**（グリフ単位の問い合わせは
しない）。`ListFontsWithInfo`（`xcb_list_fonts_with_info`）は、`QueryFont` と違って
**per-char メトリクスの配列を含まず**、`min_byte1` / `max_byte1` /
`min_char_or_byte2` / `max_char_or_byte2` / `default_char` などの FONTINFO だけを返す。
フォント選択時（§4.5.1）にこれらを控えておけば、以降は往復ゼロで判定できる。

```
UCS-2 コードポイント c を描くフォントの決定:
  byte1 = c >> 8, byte2 = c & 0xFF
  if (プライマリの範囲内) → プライマリ
  else if (補助フォントの範囲内) → 補助フォント
  else → 豆腐（□）
```

- ラン（同一フォントで描ける連続区間）に分割し、**`PolyText16` の 1 リクエストに
  フォント切替アイテムを埋め込んで**まとめて発行する（§4.5.4.1）。
  ベースラインは両フォントの `font_ascent` の大きい方に揃える。
  ラン分割の結果は §4.5.2.1 と同じくキャッシュする。
- **範囲内であっても個々のグリフが未定義である場合はある**。その文字はサーバ側で
  `default_char` に置換されて描画される（多くは豆腐）。これは §4.5.5 の best-effort の
  範囲として許容する。より正確な判定には per-char メトリクスが必要だが、
  それは §4.5.2 で禁止した `QueryFont` を要するため行わない。
- 補助フォントも見つからない場合は豆腐で描く（クラッシュも空白もさせない）。

> 当初は「描画時に文字単位でプライマリのグリフ有無を判定する」と規定していたが、
> これは実装不可能だった。グリフの有無を知る手段は per-char メトリクス
> （＝ §4.5.2 で禁止した `QueryFont`）しかなく、代替の文字単位 `QueryTextExtents` は
> §4.5.2.1 で禁じた描画経路の往復そのものになる。禁止した API を前提とする自己矛盾した
> 規定だったため、範囲判定方式に改める。

#### 4.5.4.1 `ImageText16` は使えない — `PolyText16` を使う

**`ImageText16` / `ImageText8` は、文字を描く前に文字列のバウンディング矩形を GC の
背景色で塗り潰す**（X プロトコルの定義そのもの）。タイトルバーは水平グラデーション
（§4.4）なので、これを使うと文字の背後に単色の箱が出て、§4.0 の「1 ピクセルの差も
許容しない」要求を満たせない。当初 §1.2 と本節で `ImageText16` を指定していたのは誤り
だった。

**`PolyText16` を使う。** これは前景のみを描画し、背景に触れない。加えて次の利点がある。

- **1 リクエストの中にフォント切替アイテムを埋め込める**。§4.5.4 の CJK ラン分割を、
  複数リクエストに分けずに 1 回で送れる（アイテム構造は「長さ 1 バイト + デルタ 1 バイト
  + 文字列」、長さ `255` は「次の 4 バイトがフォント ID」を表す標識）。
- テキストアイテムあたりの上限は 254 グリフ、デルタ（前のアイテムからの水平移動量）は
  符号付き 1 バイトなので、大きく飛ばす必要がある場合はアイテムを分ける。

**副作用に注意**：フォント切替アイテムを含む `PolyText16` は、**GC の `font` 属性を
変更したまま**にする。以降の描画で意図しないフォントが使われないよう、
描画関数の側でフォントを明示的に設定し直すか、GC を用途ごとに分けること。

`ImageText16` を使ってよいのは、背景が単色であることが保証されている箇所
（メニュー項目、タスクバーのボタン）に限る。ただし一貫性のため、実装では
`PolyText16` に統一し、背景は事前に矩形で塗る方式とする。

#### 4.5.5 多言語表示の保証範囲（重要）

`iso10646-1` のフォントを開けることと、そのフォントに日本語のグリフが**存在すること**は
別問題である。core ビルドは CJK のグリフデータを内蔵しない（内蔵すれば数 MB になり、
§9 の目標と正面から衝突する）。したがって保証範囲を次のように限定する。

| 条件 | 保証 |
| --- | --- |
| どんな環境でも | **起動する。ASCII / Latin-1 のタイトルは必ず描画できる**（最終手段が内蔵フォント） |
| CJK グリフを持つコアフォントが存在する | 日本語等のタイトルを表示する（**best-effort**） |
| 存在しない | 該当文字は豆腐（□）で描画し、起動時に一度だけ警告を出す |
| 確実な多言語表示が必要 | **`XFT=1` ビルドを使う**（§1.4。メモリ目標は非適用） |

**「core ビルドで日本語タイトルを必ず表示する」とは謳わない。**
当初の記述はこの点を保証できないまま断定していたため、上記に改める。

### 4.7 カーソル

Win98 の見た目を通すため、**カーソルもコアの `cursor` フォントではなく内蔵ビットマップを
使う**。`cursor` フォント（`XC_left_ptr` 等）は見た目が X11 伝統のもので、Win98 の
意匠と明確に喧嘩する。

- 1bit の Pixmap 2 枚（ソース + マスク）と `CreateCursor`（コアプロトコル）で作る。
  依存は増えない。Win98 の矢印（黒の塗り + 白の縁取り）を忠実に再現できる。
- 必要な形状：矢印、8 方向リサイズ（`↖ ↑ ↗ ← → ↙ ↓ ↘`）、移動（十字矢印）、
  砂時計（§7.4 の起動通知用）、テキスト I ビーム（メニュー等では使わないが完全性のため）。
- 各カーソルは 32×32 以内、1 形状あたり `.rodata` で約 256 B。全部で 3 KB 程度。
- 起動時に全形状を作ってサーバ側に置き、以後は `ChangeWindowAttributes` で
  ウィンドウごとに割り当てるだけ（作り直さない）。
- 配色は §4.1 に従わず固定（Win98 のカーソルはテーマ配色の影響を受けないため）。

### 4.8 タスクバー（Phase 4）

- 画面下端（設定で上/左/右も可）、高さ 28px、上端に 1px の `hilight` ライン。
- `[スタート]` ボタン（押下でスタートメニュー）、クイック起動（任意）、タスクボタン領域、
  トレイ、時計（`HH:MM`、ホバーで日付）。
- タスクボタンは押し込み＝アクティブ、点滅＝`DEMANDS_ATTENTION`。数が多い場合は幅を縮め、
  下限（既定 44px）に達したらスクロール矢印を出す（Win98 と同じ挙動）。
- 自身に `_NET_WM_STRUT_PARTIAL` を設定し、他ウィンドウの最大化領域を正しく確保する。
- 自動的に隠す（オートハイド）対応。
- **システムトレイの ARGB アイコン問題**（Phase 4 の既知の罠）：最近の常駐アプリは
  32bit ARGB ビジュアルのトレイアイコンを使うが、コンポジタが無い環境では
  アルファが解決されず背景が黒くなる。`_NET_SYSTEM_TRAY_VISUAL` に **24bit の
  ビジュアルを明示**し、アイコンを埋め込む前にトレイ側の背景を `face` 色で塗る。
  これでアプリ側が背景色を前提に描いてくれる（完全ではないが実用上これが定石）。

### 4.9 スタートメニュー（Phase 4）

- 左端の縦バナー（`#808080` グラデ + 縦書き "w98wm"）を含む Win98 の見た目。
- 項目は設定ファイルで定義（`~/.config/w98wm/menu`）。XDG の `.desktop` を走査する
  実装は**行わない**（メモリ・複雑度・起動時間の観点。必要なら外部生成スクリプトを同梱）。
- 階層メニュー、キーボード操作（矢印/Enter/Esc/アクセラレータ）に対応。

**`menu` ファイルの書式**（1 行 1 項目、空行と `#` 始まりは無視）:

```
ラベル | コマンド
-                     ← セパレータ
```

コマンドは `bind = ... exec <cmd>` と同じ規則で `/bin/sh -c` に渡す。
上限は 24 項目（`WM_MAX_START_ENTRIES`）。ファイルが無ければ組み込み項目だけが出る。

**v1.0 の実装状況（Phase 4 完了時点）:**

| 要素 | 状態 |
| --- | --- |
| 縦バナー | 実装済。ただし**文字は回転させず 1 文字ずつ縦に積む**。コアプロトコルの `PolyText16` に回転が無く、回転させるにはグリフを Pixmap へ描いて転置する必要があり、往復とメモリの両面で §9 の予算に見合わないため。**意図的な意匠差** |
| キーボード操作 | 実装済（矢印 / Enter / Esc / アクセラレータ） |
| **階層メニュー** | **未実装**。フラットな 1 段のみ。ポップアップを入れ子にすると grab の受け渡しと親メニューの選択保持が必要になるため Phase 4 の範囲から外した |

### 5.2 EWMH

#### 5.2.1 `_NET_SUPPORTED` に載せる条件

**`_NET_SUPPORTED` は「知っているアトム」ではなく「正しく実装し、テストが通っているアトム」
だけを列挙する。** クライアントはこのリストを見て挙動を変えるため、中途半端な実装を
載せると「対応しているはずなのに動かない」という最悪の状態になる。

実装上は、アトムテーブルの各エントリに `implemented` フラグを持たせ、
`_NET_SUPPORTED` の構築時にフラグが立ったものだけを書き出す。

```c
static struct atom_def atoms[] = {
    { "_NET_WM_STATE_FULLSCREEN", ATOM_SUPPORTED },   /* → _NET_SUPPORTED に載る */
    { "_NET_WM_STATE_SHADED",     ATOM_KNOWN },       /* 内部で使うが載せない */
    ...
};
```

フェーズの進行に応じてフラグを `ATOM_KNOWN` → `ATOM_SUPPORTED` に昇格させる。
CI では「`_NET_SUPPORTED` に載っている各アトムに対応する結合テストが存在すること」を
機械的に検査し、テストの無いアトムが載っていたら失敗させる。

**このテストは軽量でよい。** 求めるのは網羅的な検証ではなく「実装したつもりで動いて
いない」状態の検出であるから、1 アトムにつき `xdotool` / `xprop` を数行叩いて
期待する状態変化を確認する程度で足りる（多くは 5–10 行のシェルスクリプト）。
テストの重さで実装が止まるなら本末転倒なので、**厳密さより存在することを優先する**。

以下は **v1.0 時点で `ATOM_SUPPORTED` にする予定**の一覧であり、実装完了までは載せない。

**ルート**: `_NET_SUPPORTED`, `_NET_SUPPORTING_WM_CHECK`, `_NET_CLIENT_LIST`,
`_NET_CLIENT_LIST_STACKING`, `_NET_NUMBER_OF_DESKTOPS`, `_NET_CURRENT_DESKTOP`,
`_NET_DESKTOP_NAMES`, `_NET_DESKTOP_GEOMETRY`, `_NET_DESKTOP_VIEWPORT`, `_NET_WORKAREA`,
`_NET_ACTIVE_WINDOW`, `_NET_CLOSE_WINDOW`, `_NET_MOVERESIZE_WINDOW`, `_NET_WM_MOVERESIZE`,
`_NET_RESTACK_WINDOW`, `_NET_REQUEST_FRAME_EXTENTS`, `_NET_SHOWING_DESKTOP`。

## 7. 現代アプリ互換性

「Win98 風だが実用にならない」を避けるため、以下を明示的に受け入れ条件とする。

### 7.1 検証対象アプリ

Firefox / Chromium（サイト全画面・PiP・ポップアップ）、GTK3（gedit, nautilus）、
GTK4（gnome-text-editor）、Qt5/Qt6（qterminal, VLC）、Electron（VS Code）、
Java/Swing（globally-active フォーカス）、SDL2 ゲーム（全画面切替）、
xterm/alacritty（リサイズ増分）、mpv（全画面）、ダイアログ多用アプリ（GIMP）。

### 7.2 GTK クライアントサイド装飾（CSD）

GTK3/4 の一部アプリは自前でタイトルバーを描き、`_GTK_FRAME_EXTENTS`（影と不可視リサイズ
ボーダーの余白）を持つ。「CSD なら装飾を消す」だけでは足りず、**ジオメトリの基準が
ウィンドウ矩形から見かけの矩形へずれる**点まで規定しないと、最大化・全画面で必ず破綻する。

**用語**：ウィンドウの実矩形を `W`、`_GTK_FRAME_EXTENTS` を `(l, r, t, b)` とすると、
ユーザから見える矩形（visible rect）は `V = W − (l, r, t, b)` である。

| 局面 | 規定 |
| --- | --- |
| 装飾 | 付けない（フレームは作るがボーダー・キャプションを 0 にする） |
| ジオメトリの基準 | **`V` を基準に**配置・スナップ・エッジ吸着・タイル判定を行う。ユーザに `W` を意識させない |
| 最大化 | `V` が作業領域と一致するように `W = workarea + (l, r, t, b)` を設定する |
| 全画面 | 同様に `V` がモニタ全域と一致するようにする。GTK は全画面時に影を消して `_GTK_FRAME_EXTENTS` を **0 に更新する**ため、この値を先読みして計算してはならない |
| 状態遷移時 | 最大化・全画面・復元の**遷移のたびに `_GTK_FRAME_EXTENTS` を読み直す**。`PropertyNotify` でも追従し、変化したら現在の状態に応じてジオメトリを再計算する |
| `_NET_FRAME_EXTENTS` | CSD クライアントには `(0,0,0,0)` を設定する（WM 側の装飾は無いため） |
| 移動・リサイズ | `_NET_WM_MOVERESIZE` 経由の操作に対応すること（CSD アプリのタイトルバードラッグはこれを使う）。不可視ボーダー領域はクライアントが自前で処理するため、WM 側のボーダーヒットテストは行わない |
| ウィンドウメニュー | **`_GTK_SHOW_WINDOW_MENU` クライアントメッセージに対応する**。GTK のヘッダバー右クリックはこれを送ってくるため、未対応だと CSD アプリでウィンドウメニューを開く手段が無くなる。指定された座標にメニューを出す |
| 操作の取り消し | `_NET_WM_MOVERESIZE` の **op 11（`_NET_WM_MOVERESIZE_CANCEL`）** に対応し、開始前のジオメトリへ戻す。Esc キーによる取り消しも同じ経路で処理する |

設定 `force_ssd=true` は、`_MOTIF_WM_HINTS` を無視して強制的に装飾を付けるモード。
GTK 側のタイトルバーは消せないため二重になる。**best-effort であり推奨しない**旨を
ドキュメントに明記し、`GTK_CSD=0` 環境変数の案内を併記する。

### 7.3 リサイズの滑らかさ（`_NET_WM_SYNC_REQUEST`）

これが無いと GTK/Qt アプリのリサイズが激しくちらつく。単一スレッド・`poll(2)` ベースで
破綻なく書けるよう、状態機械として明示的に規定する。

**プロトコルの前提**（ここを取り違えやすい）：`_NET_WM_SYNC_REQUEST_COUNTER` が
**カウンタ 1 個**の場合が基本プロトコルで、WM が指定した値までクライアントがカウンタを
進めることで「その設定を反映して描画し終えた」ことを伝える。値は単調増加する
**リクエスト ID** であり、偶奇に意味はない。
偶数／奇数でフレームの途中経過を表すのは**カウンタ 2 個**の拡張プロトコル
（extended frame sync、GTK と mutter が使う）であって別物である。
**本仕様は基本プロトコル（カウンタ 1 個）のみを実装する**。プロパティに 2 個入っていた
場合は 1 個目のみを使う。当初の記述は両者を混同していたため、ここで訂正する。

**準備**（クライアント登録時に 1 回）：

```c
target = 0;
alarm = xcb_sync_create_alarm(counter,
            XCB_SYNC_CA_COUNTER | XCB_SYNC_CA_VALUE_TYPE |
            XCB_SYNC_CA_TEST_TYPE | XCB_SYNC_CA_VALUE | XCB_SYNC_CA_EVENTS,
            /* value_type */ ABSOLUTE,
            /* test_type  */ POSITIVE_COMPARISON,
            /* value      */ 1,        /* 初期の trigger 値 */
            /* events     */ true);
```

**アラームは作りっぱなしにしてはならない。** `POSITIVE_COMPARISON` は
「カウンタ値 ≥ trigger 値」で発火する仕組みなので、リクエストのたびに
`xcb_sync_change_alarm()` で **trigger 値を新しい target に更新する**必要がある。

> **`delta` に関する訂正。** 当初ここに「忘れると最初の 1 回だけ発火して
> その後は永久に沈黙する」と書いたが、これは `delta = 0` の場合に限って正確だった。
> `CreateAlarm` の **`delta` の既定値は 1** であり、その場合サーバは発火のたびに
> trigger を自動で +1 して再武装する。本仕様のように target を毎回 +1 する
> 使い方だと、`ChangeAlarm` を忘れても**偶然動いてしまう**（実装時の反証実験で
> 確認済み）。ただしクライアントのカウンタが先へ飛んだ瞬間に通知を落とすため、
> 偶然の正しさに寄りかかってはならない。
> **`CreateAlarm` で `XCB_SYNC_CA_DELTA` を 0 に明示し、再武装は必ず
> `ChangeAlarm` で行う**こと。
>
> あわせて実装上の注意: 属性値のリストは**マスクのビット値の昇順**に並べ、
> `VALUE` と `DELTA` は 64bit なので **2 ワードずつ**占める。
> ここを誤ると、エラーも出ないまま発火しなくなる。

**リサイズ 1 コマの流れ**（クライアントごとに状態を持つ）：

```
IDLE ──(ドラッグでジオメトリ変化)──> target += 1
                                     ChangeAlarm(trigger = target)
                                     _NET_WM_SYNC_REQUEST(target) を送信
                                     ConfigureWindow 送信 → WAITING
WAITING ──(XSyncAlarmNotify: counter >= target)──> IDLE
                                     （保留ジオメトリがあれば即座に次を送る）
WAITING ──(次のモーション)──> 送らずに「保留ジオメトリ」だけ更新
WAITING ──(250ms 経過)──> STALLED
STALLED ──(以降)──> 同期を諦めて §3.4.1 の 16ms レート制御のみで送り続ける
                    （AlarmNotify が返ってきたら IDLE に復帰）
```

- `XSyncAlarmNotify` を受けたら、**必ず `target` と突き合わせる**。古い（すでに
  上書きされた）リクエストに対する通知が遅れて届くことがあるため、
  `counter >= target` を満たさない通知は捨てる。
- タイムアウトは `poll(2)` のタイムアウト値に反映する。**応答しないクライアントが
  リサイズ操作全体を固まらせてはならない**（この機構で最も壊れやすい点）。
- カウンタを持たないクライアント（多くの単純な X アプリ）は最初から `STALLED` と同じ扱い。
- **一度でもタイムアウトしたクライアントは、そのセッション中「同期不適合」として記録し、
  以後のドラッグでは最初から同期を使わない**（`_NET_WM_SYNC_REQUEST` を発行せず、
  §3.4.1 のレート制御のみで動かす）。これが無いと、カウンタを持つが更新しない
  クライアントに対して**ドラッグを始めるたびに 250 ms の待ちが発生**し、操作の出だしが
  毎回引っかかる。記録はクライアント構造体のフラグ 1 bit で足りる。
  そのクライアントが後に一度でもカウンタを更新したら、記録を解除して同期に復帰させる。
- カウンタ値は 64bit（`hi`/`lo` の 2 ワード）で扱う。32bit で扱って桁上がりを落とすと
  以後アラームが二度と発火しない。

**ボタン解放時の扱い**（§3.4.1-3 との衝突を解消する）：

「未確定リクエストは 1 つまで」は**ドラッグ中のペーシング規則**であって、操作の終端には
適用しない。ボタン解放時は `WAITING` であっても、**新しい target を採番して最終
ジオメトリを即座に送る**。カウンタ値は単調増加するため、新しい target に到達した時点で
古いリクエストも自動的に充足され、古い通知は上のルールで捨てられる。整合性は保たれる。

「未確定リクエストの完了を待ってから最終ジオメトリを送る」という設計も考えられるが、
その場合ユーザがボタンを離してから最大 250 ms、ウィンドウが最終サイズにならない。
操作の終端で待たせる理由はないため、**採番し直して即送る方を採用する**。

この状態機械は移動（リサイズを伴わない）には適用しない。移動時のカウンタ更新は不要。

**アラームとカウンタのライフサイクル**（リークとエラーの原因になるため明記する）：

- クライアントの管理を解除する時（Withdrawn 遷移・破棄・WM 終了）に
  `xcb_sync_destroy_alarm` を必ず呼ぶ。**これを忘れるとサーバ側リソースが
  ウィンドウ数に比例して残り、§9.1 の指標 C（サーバ側リソースがウィンドウ数に対して
  線形）を静かに破る。** 通常操作では表面化しないので、テストで検出すること。
- クライアントは終了時に自分のカウンタを破棄する。これはアラームより先に起きうるため、
  カウンタ由来のエラー（`BadAlarm` / `XSyncBadCounter`）は §2.2.2 の方針に従って
  無視し、`sync_state` を「カウンタ無し」に落として `STALLED` 相当で続行する。
- `_NET_WM_SYNC_REQUEST_COUNTER` プロパティが差し替えられた場合
  （`PropertyNotify` で検知）、古いアラームを破棄して新しいカウンタで作り直す。
- プロパティに 2 個のカウンタが入っている場合は 1 個目のみを使う（前述）。

### 7.4 その他

- `_NET_WM_PING` による無応答検出。無応答ウィンドウはタイトルに `(応答なし)` を付け、
  閉じる操作で「プログラムの終了」ダイアログ（Win98 風）を出す。
- **強制終了の手段は `KillClient`（`xcb_kill_client`）を主とする。** X 接続ごと切るため
  PID を必要とせず、リモート表示のクライアントにも正しく効く。
  `_NET_WM_PID` を使った `kill(2)` は、**`WM_CLIENT_MACHINE` がローカルホスト名と
  一致する場合に限り**補助的に使う（PID は表示元ホストのものであり、一致を確認せずに
  シグナルを送ると無関係なローカルプロセスを殺す）。
- 起動通知：プロトコルの実体は**プロパティではなくルートウィンドウ宛の
  `_NET_STARTUP_INFO_BEGIN` / `_NET_STARTUP_INFO` クライアントメッセージ列**であり、
  20 バイトずつに分割された文字列を連結して `new:` / `remove:` メッセージを解釈する。
  最小実装として、`new:` を受けたら ID を記録して砂時計カーソルを表示し、
  対応する `remove:`、または同じ `_NET_STARTUP_ID` を持つウィンドウのマップ、
  あるいは 15 秒のタイムアウトで解除する。同時に追跡する ID は 8 個まで。


パースは起動時のみ。`SIGHUP` で再読み込み。パーサは行単位・スタックバッファ 512B で処理し、
結果は固定サイズ構造体＋キーバインド配列（最大 128 個 = 約 2 KB）に格納する。

## 9. メモリ目標と測定方法

### 9.1 目標の定義（重要）

「1 MB 未満」は測り方で結果が変わるため、次のように定義する。

| 指標 | 目標 | 説明 |
| --- | --- | --- |
| **A. プライベートダーティ（主目標）** | **< 1024 KB** | `/proc/self/smaps_rollup` の `Private_Dirty`。ヒープ・スタック・.data/.bss・再配置分。プロセスが実際に「消費している」メモリ。**Linux でのみ測定可能**（下記） |
| B. VmRSS（参考値） | < 3 MB 目安 | 共有ライブラリのテキスト（libc/libxcb）を含む。他プロセスと共有されるページも含むため、本目標の主指標にはしない |
| C. X サーバ側リソース | 記録する | ウィンドウ数・Pixmap（アイコンキャッシュ）の合計。`xrestop` で計測 |

**測定条件は 1 点ではなく 4 点取る**。単一条件だけだと、CI で閾値割れしたときに
「常駐の底が上がったのか／ウィンドウあたりの単価が増えたのか／リークしたのか」を
切り分けられないため。

| 条件 | 内容 | 判定基準 | この数値が読み取れること |
| --- | --- | --- | --- |
| M0 | 起動直後・ウィンドウ 0 枚・タスクバー無効 | `< 400 KB` | **常駐の底**（.data/.bss・再配置・xcb 接続・起動時確保） |
| M1 | 起動直後・ウィンドウ 0 枚・タスクバー/トレイ有効 | `< 550 KB` | シェル部分の固定費 |
| M20 | 20 ウィンドウ・タスクバー/トレイ有効 | `(M20 − M1) / 20 < 2 KB` **かつ** `M20 < 1024 KB` | ウィンドウあたりの限界費用 |
| M20h | M20 の状態で 1 時間稼働 + 500 回の開閉/移動/リサイズ | `M20h − M20 < 32 KB` | **リークの有無**（増分が単調なら断片化ではなくリーク） |

**M20 の判定は 2 条件の AND である。** 当初は「M20 < 1024 KB」とだけ書き、本文で
「2 KB/窓未満」と述べていたが、この 2 つは整合していなかった。M1 < 550 KB と
M20 < 1024 KB からは 23.7 KB/窓まで許容されてしまい、本文の主張を担保できない。

実質的に効くのは**限界費用の条件**の方である。M1 = 550 KB・2 KB/窓なら M20 は
約 590 KB に収まり、1024 KB には十分な余裕がある。この余裕は意図的なもので、
1 MB は**対外的に約束する上限**、限界費用の条件は**回帰をその場で検出するための
CI ゲート**という役割分担にする。窓あたりの単価が太った瞬間に、
まだ 1 MB に達していなくても CI が落ちる。

CI ではこの 4 点すべてを記録し、いずれかが基準を超えたらビルドを失敗させる。
これによりフェーズごとのコミットで「どこが太ったか」が履歴から追える。

参考として、Metacity は約 15–25 MB、Openbox は約 5–8 MB、i3 は約 4–6 MB（VmRSS）。
本プロジェクトは B の指標でも Openbox の 1/3 以下を狙う。

**OpenBSD では指標 A を測定できない。** `smaps_rollup` 相当の内訳を得る手段が無いため、
指標 A は **Linux でのみ判定する**。OpenBSD では `ps -o rss` と `procmap(1)` による
参考値を記録し、「Linux で測った値から大きく乖離していないこと」を確認するに留める。
§10 の受け入れ条件および PLAN Phase 5 の完了条件も、この区別に従う。

### 9.1.1 目標が未検証であることの明示と、反証時の判断規則

**§9.1 の数字はすべて予測であり、実測に基づいていない。** 実装が 1 行も無い時点で
「1 MB 未満」と書いている以上、これは設計というより仮説である。この事実を隠さず、
**仮説が反証されたときに何をするかを先に決めておく**。判断を後回しにすると、
目標に固執して機能を歪めるか、目標を黙って忘れるかのどちらかになる。

**検証点**：Phase 1 完了時（コア WM が動き、20 ウィンドウを開ける状態）に M0/M1/M20 を実測する。
この時点で全機能の約 4 割が入っており、残りの増分は経験的に見積もれる。

**判断規則**（Phase 1 の実測値に対して、この順で適用する）：

| Phase 1 実測 M20 | 判断 | 行動 |
| --- | --- | --- |
| < 400 KB | 目標は達成可能 | そのまま全機能を実装する |
| 400–700 KB | 達成は微妙 | 残りのフェーズで実測しながら進め、Phase 4 完了時に再判定する |
| 700 KB–1 MB | 全機能では超過が濃厚 | **下記の削減順序**を発動する |
| > 1 MB | 設計前提が誤り | 目標を実測値ベースで再設定し、§11 の決定 #1 を撤回して再承認を得る |

**削減順序**（メモリを削る必要が生じた場合、この順に落とす。上ほど先に切る）：

1. **システムトレイ**（XEmbed。最も複雑で、外部トレイに代替可能）
2. **スタートメニュー**（外部ランチャに代替可能）
3. **タスクバー**（外部パネル tint2 等に代替可能。§11 の決定 #3 を見直す）
4. 仮想デスクトップの多面対応（1 面固定にする）
5. 配色プリセット（Windows Standard のみにする）

1–3 はいずれも `taskbar=false` 相当のコンパイル時除外が既に仕様に入っているため、
**削減は機能を削るだけで済み、アーキテクチャの作り直しにはならない**。
逆に言えば、削減順序を先に決めておくことの価値はここにある。

**目標を下げる場合の代替値**：実測が 1–3 MB に収まるなら、それでも
Openbox（5–8 MB）や Metacity（15–25 MB）に対する優位は保てる。
「1 MB」は看板として魅力的だが、**看板のために機能を削るか、
実測に合わせて看板を書き換えるかは、実測を見てから決める**。

### 9.2 達成手段

1. core ビルドでは Xlib / fontconfig / FreeType / GLib / cairo を一切リンクしない（§1.4）。
2. クライアント情報はスラブ確保（64 個 × 約 448 B = 28 KB/チャンク。
   タイトルキャッシュ 256 B を含む。§2.3.1 の通りこれは意図した支出である）。
3. アイコンのピクセルデータをクライアント側に常駐させない（§4.4.1）。
   大きなプロパティは分割読み込みでピーク使用量も抑える。
4. 描画バッファを持たない（サーバ側 GC + 直接描画。ダブルバッファはタスクバーのみ、
   サーバ側 Pixmap 1 枚で行う）。
5. 16bit フォントへの `QueryFont` を禁止（§4.5.2）。数百 KB の一時リプライを避ける。
6. ビルド: `-Os -fno-plt -fno-asynchronous-unwind-tables -ffunction-sections
   -fdata-sections -Wl,--gc-sections`、`-fno-stack-protector` は**使わない**（安全性優先）。
7. 設定パース用バッファ・起動時の一時領域は起動完了後に解放し、`malloc_trim` を呼ぶ
   （glibc のみ）。

なお **musl 静的リンクはこの一覧に含めない**。静的リンクが減らすのは共有ライブラリの
ファイルバックドなページであり、これは元々 `Private_Dirty` に計上されない。
指標 A の改善手段ではないため、§1.4 の通り配布利便性のための experimental 扱いとする。

### 9.3 継続的な計測

CI（GitHub Actions）で Xvfb 上に §9.1 の M0 / M1 / M20 / M20h を再現し、
`smaps_rollup` の `Private_Dirty` を読んで**目標を超えたらビルドを失敗させる**
（M20h のみ実行時間の都合で毎コミットではなく nightly）。
数値は `docs/MEMORY.md` に履歴として追記し、フェーズごとの推移を残す。

## 10. 受け入れ条件

以下がすべて満たされた時点で v1.0 とする。

1. §7.1 の全アプリが起動・移動・リサイズ・最大化・全画面・閉じるを正常に実行できる。
2. `xprop -root _NET_SUPPORTED` が §5.2 の全アトムを列挙し、`wmctrl -m` が正しく応答する。
3. Win98 実機スクリーンショットとの比較で、フレーム・タイトルバー・ボタンの
   ピクセル差分が意匠部分でゼロ（フォントとグラデーション量子化を除く）。
4. §9.1 の指標 A が 1024 KB 未満（**Linux で測定**。OpenBSD は参考値の記録のみ）。
5. Linux（glibc/musl）と OpenBSD の両方でビルド・動作する。
6. 8 時間の連続稼働でクラッシュ・リークが無い（valgrind + ストレススクリプト）。
7. **WM がクラッシュしても管理下のウィンドウが失われない。**
   検証は `kill -9`（graceful path を通らない終了）で行う。セーブセット（§3.1.1）が
   正しく機能していれば、全ウィンドウがルート直下に復帰して生き残る。
   `SIGTERM` による正常終了では、加えて自前のクリーンアップ（ルートへの reparent、
   `WM_STATE` の削除）が走ること。
